## 初学者导读（请先读这里）

### 这个文件是做什么的？

这份文档是 ZT-DSP 通信协议的**总指导**，同时承担三件事：规范定义、使用说明、教学讲稿。它定义了五件核心事情：

1. 两台设备如何**互相找到对方**（门牌号机制，第三册、4.1 节）
2. 两台设备如何**确认彼此身份**（令牌机制，4.1 节）
3. 两台设备如何**加密通信**（四阶段握手，4.2 节）
4. 遇到攻击时协议如何**防御**（第五册）

### 它为什么存在（解决什么问题）？

在互联网上通信，默认情况下任何人都可能偷看、篡改你的消息。ZT-DSP 要解决的问题是：**在「不信任任何人」的前提下，让两个已经认识彼此的人安全地通信**。

设想这样一个场景：你想给朋友寄一封信，但邮局工作人员可能偷看内容、可能伪造信件。ZT-DSP 提供了一套方法，让邮局只能帮你送信，却永远无法知道信里写了什么，也无法伪造一封"看起来是你写的"信。（以上为设想，非技术描述）

# 第一册：核心思想与设计原则

> **【本册导读】** 这一册回答三个问题：① 什么是"零信任"？② 什么是"动态同步"？③ 协议遵循哪四项核心原则？本册是全部后续内容的思想基础——如果你理解了本册，第四册的技术细节就有了"为什么"的答案。
>
> **【初学者关注点】** 重点理解 1.1 和 1.3 的四项原则，尤其是"带外交换"和"静默丢弃"——它们会在后面反复出现。
>
> **【前置知识】** 无。本册只需要日常生活经验。

## 1.1 什么是"零信任"？

```plain
零信任（Zero Trust）
├── 含义：一种安全设计思想——默认不信任网络中的任何人或任何环节，直到被密码学证据证明可信
├── 原理：把"信任"从人的道德、机构的声誉中剥离，只交给数学（密码学）。因为人会犯错、机构会被攻破，但数学规律不会
└── 出发方向：传统安全模型假设"内网可信、外网不可信"，但现实中内网攻击（内部人员、被攻破的服务器）才是主要威胁来源，因此诞生了"永不信任，始终验证"的模型
```

在传统的网络通信中，我们通常假设某些环节是可信的。比如，我们假设聊天软件的服务器不会偷看聊天记录，假设电信运营商不会篡改短信内容。但 ZT-DSP 的设计原则是：**不假设任何人可信**。

> **生活类比**：设想这样一个场景：传统安全像小区门禁——进了小区大门就默认是"自己人"。零信任像机场安检——就算你已经过了第一道安检，登机口前还要再查一次，没有任何一个环节可以"刷脸免检"。
> （以上为设想，非技术描述）

"零信任"意味着：

- 不假设服务器诚实——服务器可能试图窥探你的通信
- 不假设网络路径安全——中间人可能截获、篡改、重放你的数据包
- 不假设认证机构永久可靠——TCA 可能被攻破、被胁迫、被关闭
- 只假设数学可靠——基于密码学的数学原理，而非人的道德

> **常见误区**：零信任 ≠ "完全不信任任何人、无法协作"。零信任不是拒绝信任，而是**用可验证的凭证代替口头承诺**——它只是把信任的来源从"身份/位置"换成了"数学证据"。

## 1.2 什么是"动态同步"？

"动态"指的是协议的状态不是静态的。每一轮通信都会更新密钥，每一次会话都会生成新的加密上下文。"同步"指的是通信双方通过数学方式达成状态一致——双方独立计算出相同的密钥，而不需要第三方参与。

> **生活类比**：设想这样一个场景：动态同步像"对表"——两个人各看各的表，但通过同一套规则（比如都听同一声整点报时）让时间保持一致。ZT-DSP 中，双方各自持有相同的材料（PSK、DH 结果、会话盐），用同一套公式独立计算出完全相同的密钥——不需要第三方"帮他们约定"。
> （以上为设想，非技术描述）
>
> **关键术语预告**：本段提到的"密钥"（Key）在术语对照表中有说明。通俗地说：密钥就是一把"数字锁的钥匙"，用它加密的消息，只有持有同一把钥匙的人才能解开。

## 1.3 四项核心原则

### 原则一：协议公开，实现自由

ZT-DSP 的所有规范都是公开的。任何人可以阅读、修改、实现自己的版本。没有**必须使用的**官方客户端，没有强制更新，没有中心化控制。这种开放性既是协议的优势，也是其安全性的来源——攻击者无法通过攻破一个官方客户端来控制整个网络。

> **关联知识**：这类似开源软件（Open Source）的理念——代码公开不意味着不安全，"安全靠公开审查"（Kerckhoffs 原则：即使攻击者知道系统的全部设计，只要密钥保密，系统仍然安全）。Kerckhoffs 原则在术语对照表中有说明。

> **常见误区**：很多人以为"协议公开 = 漏洞被攻击者看到 = 不安全"。恰恰相反：公开协议经过无数人审查，漏洞会被更快发现和修复；保密的协议（Security by Obscurity，靠隐瞒实现安全）反而常在公开后被证明千疮百孔。

### 原则二：参数自治，静默丢弃

每个服务器运营者可以定义自己的"方言"——特定的参数组合。不符合参数的数据包会被直接丢弃，不返回错误，不触发处理。这种"静默丢弃"机制使得端口扫描和协议探测变得极其困难：攻击者无法区分"端口关闭"和"参数不匹配"。

```plain
静默丢弃（Silent Drop）
├── 含义：服务器收到不符合参数声明的数据包时，不返回任何响应、不记录日志、不消耗计算资源，表现得像端口根本不存在
├── 原理：错误信息是攻击者的"情报源"。如果服务器对每种错误返回不同的错误码，攻击者就能通过试错推断出协议的参数细节；不回应 = 不给情报
└── 出发方向：传统协议（如 HTTP）会返回 400/404 等错误码，便于调试但也便于探测。匿名网络协议需要"隐身"，因此诞生了静默丢弃
```

> **生活类比**：设想这样一个场景：静默丢弃像一间"没有招牌的密室"——敲门没人应、喊话没人答，路人无法判断里面到底有没有人、锁是什么型号。
> （以上为设想，非技术描述）

### 原则三：带外交换，门牌号先行

在 ZT-DSP 中，你不能像加微信好友那样"搜索用户名"然后添加。你必须在进入网络之前，就已经通过某种安全渠道（面对面、加密邮件、二维码等）获得了对方的"门牌号"。这不是设计缺陷，而是匿名性的根本保障。

```plain
带外交换（Out-of-Band Exchange）
├── 含义：通过"通信网络之外"的渠道交换信息（面对面、信件、已确认安全的另一个信道），而不是在 ZT-DSP 网络内部交换
├── 原理：网络内部的交换可能被监控、被篡改；带外渠道不经过网络，中间人无法同时控制两个渠道，因此可以作为"信任的起点"
└── 出发方向：任何加密通信都需要一个"初始信任"——双方必须先确认"对方确实是那个人"。带外交换提供了这个初始信任，且不依赖任何中心化机构
```

> **常见误区**：带外交换 ≠ 必须线下见面。二维码扫描、加密邮件、已经建立信任的其他聊天工具都算带外。核心判断标准是：**这个渠道不经过 ZT-DSP 服务器，且你已确认它可信**。

### 原则四：分层隔离，权限最小化

协议中的每个角色（TCA、服务器、客户端）只拥有完成其功能所必需的最小权限。TCA 只发身份证，不进入房间；服务器只转发包裹，不打开箱子；客户端只管理自己的密钥，不干涉他人。

```plain
最小权限原则（Principle of Least Privilege）
├── 含义：每个角色/程序/用户只被授予完成其任务所必需的最小权限，不多给一分
├── 原理：权限越大，被攻破时的破坏范围越大。把权限压缩到最小，即使某个环节被攻破，损失也被限制在局部
└── 出发方向：安全界长期教训——大量数据泄露事故源于"某个员工账号权限过大"。最小权限是安全设计的第一性原则
```

> **关联知识**：最小权限原则也广泛应用于操作系统（如 Linux 非 root 用户运行服务）、数据库（只读账号）、云服务（RAM 角色）中。学会这一原则，你在任何技术领域都能用上。

## 3.1 为什么要用酒店来比喻？

密码学协议往往充满抽象概念——哈希、密钥派生、前向安全、中间人攻击。对于初学者来说，设想这样一个场景：这些术语像一堵墙。酒店模型将这堵墙变成了一扇窗：通过日常生活中熟悉的场景，理解协议的安全边界。（以上为设想，非技术描述）

> **重要提醒**：**酒店模型是教学工具，不是技术规范。** 当你需要精确实现时，请回到第四册的数学描述。模型中的比喻（如"箱子"）在技术上对应具体的加密算法（AES-256-GCM），不要混用。

## 3.2 场景设定

设想这样一个场景：一家特殊的酒店——

- 任何人都可以建造自己的酒店（部署服务器）
- 酒店前台不认识任何住客（匿名性）
- 酒店保安只验证身份证真伪，不记录谁来找谁（TCA 职能）
- 房间没有钥匙孔，前台无法进入（端到端加密）
- 住客进入房间前，必须已经知道对方的房间号（带外交换）

> **生活类比升级**：设想这样一个场景：这家酒店更像"快递中转站 + 星级酒店"的混合体——前台负责把包裹从 A 房运到 B 房，但前台既没有开箱钥匙，也不登记包裹内容。
> （以上为设想，非技术描述）

## 3.3 角色映射

| 酒店中的角色 | ZT-DSP 中的实体 | 功能说明 |
|--------------|------------------|----------|
| 酒店 | 服务器（Server） | 提供连接场所，转发数据包 |
| 前台 | 服务器软件 | 登记、匹配、转发，不解密 |
| 保安 | TCA（令牌认证机构） | 签发身份证，验证真伪 |
| 管家 | TCA 巡检程序 | 定期检查证件是否过期或被吊销 |
| 房间 | 匹配池（配对空间） | 只有持有相同门牌号的双方能进入 |
| 大厅 | 候补区（等候池） | 存放尚未匹配到对方的临时设备 |
| 住客 | 客户端设备 | 实际通信的双方 |
| 箱子 | 加密数据包 | 前台只能看到外观，无法打开 |
| 门牌号 | 令牌哈希 H(Token) | 用于寻找对方的标识符 |

## 3.4 五条核心规则

### 规则一：门牌号不是到酒店才领的

你去酒店找朋友，不是到前台问"我朋友住哪间"，而是出发前朋友就已经把房间号告诉了你（通过微信、电话、纸条）。在 ZT-DSP 中，这个"提前告知"就是带外交换——通过二维码扫描、加密邮件、线下见面、P2P 直连等方式，双方在进入任何服务器之前就已经知道彼此的门牌号（令牌哈希）。

**如果你没带门牌号，酒店前台不会告诉你任何人的房间号。这不是 bug，这是匿名性的底线。**

> **实践提示**：门牌号（令牌哈希）是**公开信息**，可以放心告诉朋友；但门牌号背后的"令牌本体"（身份证）是**绝密信息**，永远不能给别人。设想这样一个场景：你可以把电话号码印在名片上，但绝不能把身份证原件交给别人。（以上为设想，非技术描述）

### 规则二：前台无法打开任何箱子

住客 A 和 B 进入房间后，开始交换箱子。每个箱子都上了锁，钥匙只有 A 和 B 拥有。前台负责将箱子从 A 的房间运到 B 的房间，但前台没有钥匙，无法打开箱子查看内容。即使前台恶意，它最多只能做两件事：拒绝运送（断网）或者延迟运送（降速），但永远无法知道箱子里是什么。

> **关联知识**：这就是"端到端加密"（End-to-End Encryption）——加密和解密只发生在通信两端，中间环节（服务器）永远只看到密文。微信、Signal 等即时通讯软件的"端到端加密"宣传的也是同一原理。

### 规则三：保安不进入房间

保安（TCA）的职责是在酒店门口验证住客的身份证是否伪造。验证通过后，保安不会跟着住客进入房间，也不会知道住客要找谁、在房间里说什么。保安甚至不住在这家酒店里——他可能在另一个城市，只是通过数字签名来验证身份证的真伪。

```plain
数字签名（Digital Signature）
├── 含义：用私钥对数据生成的"防伪印记"，任何持有对应公钥的人都能验证印记真伪，但无法伪造
├── 原理：私钥签名、公钥验证——签名者用只有自己知道的私钥生成签名；验证者用公开的公钥检查签名是否匹配，不匹配则数据被篡改或签名者身份可疑
└── 出发方向：现实中的手写签名可以模仿；数字签名由数学保证不可伪造，是电子身份认证的基石
```

> **实践提示**：保安验证身份证时，用的是"验证算法"（公钥验证），不需要看到身份证的全部内容——设想这样一个场景：安检员只需要验证护照芯片真伪，不需要知道你护照上所有的出入境记录。这就是为什么 TCA 可以不持有你的任何通信数据。（以上为设想，非技术描述）

### 规则四：大厅里的住客互相不可见

当 A 来到酒店，出示门牌号寻找 B，但 B 尚未到达。A 会被安排在大厅（等候池）等待。**关键安全特性：大厅里的所有住客互相不知道对方的存在。** A 不知道大厅里还有 C、D、E；C、D、E 也不知道 A 在等谁。前台不会广播"A 在等 B"，只是默默保存这条记录。

> **生活类比**：设想这样一个场景：这像"匿名会客厅"——所有等待者都在同一个房间里，但每个人都被隔板隔开，谁也看不见谁，只有前台知道每个人的位置。
> （以上为设想，非技术描述）

> **关联知识**：这对应密码学中的"不可观察性"（Unobservability）——不仅内容保密，连"谁在和谁通信"这种元数据也不暴露。注意：元数据（谁、何时、多频繁）往往比内容本身更能暴露隐私，这也是 4.2.4 节加密令牌哈希的原因。

### 规则五：房间一旦配对，外人无法闯入

当 B 终于到达，前台核对门牌号匹配，将 A 和 B 送入同一房间。从这一刻起，这个房间被锁定。如果有第三方 C 也持有相同的门牌号哈希（理论上可能，但概率极低），试图加入这个房间，前台会直接拦截并丢弃其请求。这个被保护的占位空间就是"虚拟房间"——它存在，但对外不可见、不可进入。

```plain
哈希（Hash，哈希函数）
├── 含义：把任意长度的数据"压缩"成固定长度字符串（如 256 位）的函数；同样输入永远得到同样输出，输入差一点输出面目全非
├── 原理：单向函数——从输入算输出容易，从输出反推输入在计算上不可行（除非暴力穷举）；不同的输入产生相同输出的概率极低（抗碰撞）
└── 出发方向：需要"指纹"的场景——验证数据完整性、存储密码（只存哈希不存明文）、生成公开标识符（门牌号）
```

> **常见误区**：哈希 ≠ 加密。加密是可逆的（有钥匙就能还原明文）；哈希是不可逆的（只能验证、不能还原）。把密码只存哈希、把哈希当加密用，都是新手常犯的错误。

## 4.1 身份与凭证体系

> **【版本支持声明 · TPM 与 HWID】** 本节中关于 TPM（可信平台模块）与 HWID（硬件标识）的存储、绑定与写入描述，是 ZT-DSP 在**协议层面**的设计目标，**当前 1.0.0 发行版尚未实现**。官方客户端 `zt_dsp_py` 与 `zt_dsp_rs` **不支持对 TPM 或 HWID 的任何写入、读取或修改操作**；PSK 与令牌目前以普通配置方式（`--psk-file` / `--psk-env` / `--psk`）由调用方提供，其保密性由调用方自行负责，客户端不做硬件级保护。该能力**计划在后续版本中更新**，届时本节各条「存储位置 / 物理绑定 / 不可导出」的表述才会对应到可运行的代码。本节凡出现 TPM/HWID 之处，均以本声明为准。

在 ZT-DSP 中，你的身份由两部分组成：

1. **令牌（Token）**——你的"身份证"，由 TCA 签发，协议设计上应存储在设备的 TPM/HWID 中（**1.0.0 未实现 TPM/HWID 存储，见本节开头的版本支持声明**）
2. **令牌哈希（H(Token)）**——你的"门牌号"，用于在服务器上寻找对方

```plain
Token（令牌）
├── 含义：由 TCA 签发、经数字签名保护的设备身份凭证，设想这样一个场景：它相当于"数字身份证"（以上为设想，非技术描述）
├── 原理：令牌内含随机种子（核心熵源）与 TCA 的 Ed25519 签名；任何人可用 TCA 公钥验证签名真伪，但无法伪造（没有 TCA 私钥）
└── 出发方向：网络中需要一种"无法伪造、可离线验证"的身份证明，令牌因此而生
```

**关键区别：身份证是秘密的，门牌号是公开的。** 你永远不会把身份证给别人看，但你可以把门牌号告诉朋友，让他们在酒店里找到你。

> **生活类比**：设想这样一个场景：令牌像身份证原件（含芯片信息，绝不外借）；令牌哈希像身份证号码（可以印在表格上，用来被别人识别）。身份证号泄露不等于身份被窃取——但配合其他信息仍可能被滥用，所以两者都要妥善保管。
> （以上为设想，非技术描述）

> 【隐私风险】令牌一旦泄露（如设备被植入恶意软件、备份文件被窃取），攻击者可冒充你的身份参与任何会话。令牌哈希（门牌号）虽可公开，但长期使用同一门牌号会被服务器或监控者用于关联你的行为轨迹（流量分析）。
>
> 【防护建议】令牌只存于 TPM/HWID（硬件安全区），不落盘明文、不导出、不备份；如需更换身份，可申请新令牌并更换门牌号。（**1.0.0 未实现 TPM/HWID 存储**：这是协议层面的目标状态，当前客户端把令牌当作普通配置处理，硬件级保护需由部署方自行提供）
>
> 【合规提示】令牌属于"身份标识数据"，应遵循**最小化原则**：仅存储完成协议功能所必需的字段（见 4.1.1 字段表），不写入任何个人身份信息（姓名、手机号等），以减少数据泄露时的损害。

### 4.1.1 令牌结构

令牌是一个 256 位的数据结构，包含以下字段：

| 字段名称 | 长度 | 说明 |
|----------|------|------|
| 厂商标识（可选） | 32 位 | 自定义，可全随机。用于标识设备制造商或社区 |
| 设备类型（可选） | 16 位 | 自定义，可全随机。用于标识设备类型（手机、路由器、IoT 传感器等） |
| 用户自定义（可选） | 64 位 | 自定义，可全随机。用户可自行定义用途 |
| 随机种子 | 128 位 | **必需。** 真随机数，是整个令牌的核心熵源 |
| 校验和 | 16 位 | CRC-16，仅用于传输过程中的意外损坏检测 |

```plain
熵（Entropy）
├── 含义：随机性的度量。熵越高，数据越不可预测；128 位熵意味着有 2^128 种等可能取值
├── 原理：密码学安全依赖"攻击者猜不到"。随机种子若可预测（如用时间戳生成），整个令牌体系就可被攻破
└── 出发方向：为什么需要真随机？因为伪随机生成器（如果种子可预测）会让"随机"变成"可预测"，密码学中可预测 = 不安全
```

```plain
CRC-16（Cyclic Redundancy Check，循环冗余校验）
├── 含义：一种 16 位的校验码，用于检测数据在传输/存储中的意外损坏（如比特翻转）
├── 原理：把数据当作多项式做除法，余数即校验码；接收方重算比对，不一致说明数据被改动
└── 出发方向：传输介质（网线、Wi-Fi、电磁干扰）会随机损坏比特。注意：CRC 只能检测**偶然损坏**，不能防**恶意篡改**（攻击者可以重算 CRC），防篡改靠的是 Ed25519 签名和 GCM 认证标签
```

> **常见误区**：CRC 校验 ≠ 完整性保护。CRC 是"粗心检测"（防意外），数字签名/GCM 是"严格认证"（防恶意）。把 CRC 当作防篡改手段是新手常见误解。

**令牌哈希 = SHA-3-256（完整令牌）**

> **补充（P2P 直连占位路径）**：以上是"有 TCA 令牌"时的标准算法。但**无 TCA 的纯 P2P 直连**场景（官方客户端默认模式）没有令牌本体，此时官方客户端用 PSK 派生**占位令牌哈希**：

```plain
占位令牌哈希 = HMAC-SHA3-256(PSK, 角色标签) 的前 32 字节
角色标签 = "ZT-DSP-TOKEN-INITIATOR-v3"（自己作为发起方时）
        或 "ZT-DSP-TOKEN-RESPONDER-v3"（自己作为响应方时）
```

- 发起方用自己的门牌号 = HMAC(PSK, "ZT-DSP-TOKEN-INITIATOR-v3")、对端的门牌号 = HMAC(PSK, "ZT-DSP-TOKEN-RESPONDER-v3")；**响应方两个标签对调**（自己用 RESPONDER 标签、对端用 INITIATOR 标签）。这样 A 的 src 恰好等于 B 的 dst，保证阶段四令牌哈希双向校验自洽
- 该路径只保证**帧结构完整**与**双方身份绑定 PSK**，不具备 TCA 的"第三方公证"属性；需要公证身份时仍应挂载 TCA 模块注入真正的令牌哈希

```plain
SHA-3-256（Secure Hash Algorithm 3，安全哈希算法第三代，256 位输出）
├── 含义：NIST 标准化的哈希函数，把任意长度输入压缩为固定 256 位输出
├── 原理：基于 Keccak 海绵结构（Sponge Construction）——吸收输入、挤压输出；单向性 + 抗碰撞性由数学结构保证
└── 出发方向：NIST 于 2015 年标准化 SHA-3，作为 SHA-2 家族的备份方案，避免"单一算法被攻破则全行业瘫痪"
```

### 4.1.2 令牌的颁发与 TCA 联邦

**TCA（Token Certification Authority，令牌认证机构）的职责：**

```plain
TCA（Token Certification Authority，令牌认证机构）
├── 含义：为设备签发令牌并维护吊销列表的第三方机构，类似现实中的"公安局 + 公证处"
├── 原理：TCA 持有自己的 Ed25519 私钥，用它给令牌签名；验证方只用 TCA 公开的公钥即可验证令牌真伪，无需联系 TCA 本人
└── 出发方向：没有 TCA，任何人都能无限生成假身份（Sybil 攻击），公益服务器会被垃圾连接淹没；TCA 提供"身份成本"，同时通过联邦化避免中心垄断
```

1. 验证申请者身份（验证程度由各 TCA 自行决定）
2. 签发令牌并附加 Ed25519 数字签名
3. 维护吊销列表（CRL），标记已失效的令牌
4. 响应服务器对令牌状态的查询

```plain
CRL（Certificate Revocation List，证书吊销列表）
├── 含义：记录已被作废令牌（身份证）的名单，服务器在验证时查询该名单
├── 原理：TCA 定期发布名单；服务器验证令牌时同步检查"这张证是否已被吊销"
└── 出发方向：令牌可能因设备丢失、私钥泄露、滥用被封禁而被作废；没有吊销机制，作废的令牌将永远有效
```

**TCA 联邦模型：**

- 任何人可以自建 TCA。只要你生成一对 Ed25519 密钥，你就可以开始为朋友签发令牌
- 一台设备可以持有多个 TCA 颁发的多个令牌（设想这样一个场景：就像同时拥有身份证、护照、驾照）（以上为设想，非技术描述）
- 一台服务器可以持有多个 TCA 的白名单，服务器运营者可声明"我认可 TCA-A 和 TCA-B 签发的令牌，但不认可 TCA-C"
- TCA 的权威性取决于社区认可。没有强制垄断机构，没有"根 CA"

> **关联知识**：TCA 联邦与 HTTPS 的 CA（证书颁发机构）体系类似，但有一个关键区别：HTTPS 有"根 CA"（浏览器预装信任列表），ZT-DSP 没有——每个服务器自己决定信任谁。这是"去中心化信任"的设计。

> 【隐私风险】TCA 在签发令牌时可能获知你的设备信息（取决于其验证流程）。TCA 不参与通信、不持有通信密钥，但它持有的"设备—令牌"对应关系是敏感数据，若 TCA 被攻破或胁迫，可能泄露你的身份关联信息。
>
> 【防护建议】选择验证程度低的 TCA（如仅验证设备存在性）；多令牌轮换使用；服务器运营者不应向 TCA 索要超出"签名验证"所需的信息。
>
> 【合规提示】TCA 作为"身份数据处理者"，应遵循数据最小化原则，仅在签发/吊销流程中收集必要信息，并明确告知申请者数据用途与保留期限。

### 4.1.3 授权码（可选加强层）

部分服务器要求客户端除令牌外，还需提供授权码。授权码由 TCA 颁发并与特定服务器绑定，协议设计上由设备在首次接入时将其写入 TPM/HWID（**1.0.0 未实现写入 TPM/HWID，待后续版本更新**）。服务器可据此对每一台设备进行单独管理（封禁、禁言、限流）。没有授权码的客户端，即使持有合法令牌，也无法进入要求授权码的服务器。

- **令牌 = 身份证**：证明"你是一个合法的人"
- **授权码 = 门禁卡**：证明"你被允许进入这家特定的酒店"

> **生活类比**：设想这样一个场景：令牌是身份证（全国通用），授权码是公司门禁卡（只对这家公司有效）。丢失门禁卡不影响身份证效力；吊销门禁卡也不会影响你在其他服务器的身份。
> （以上为设想，非技术描述）

### 4.1.4 设备专属密钥（PSK）

PSK（Pre-Shared Key，预共享密钥）是 ZT-DSP 安全体系的核心锚点。

- **长度**：256 位真随机数
- **存储位置**：协议建议为设备的 TPM（可信平台模块）或 HWID（硬件标识）；**1.0.0 未实现，实际由调用方以配置文件或环境变量自行保存**
- **特性**：协议目标为物理绑定、不可导出、不可复制；**1.0.0 不具备上述硬件保护能力，待后续版本更新**
- **用途**：参与会话密钥派生，是穿越所有通信场景的根信任基础

```plain
TPM（Trusted Platform Module，可信平台模块）
├── 含义：焊在主板上的独立安全芯片，专门用来安全生成和存储密钥
├── 原理：密钥生成和签名运算在芯片内部完成，私钥永不出芯片；即使操作系统被攻破，攻击者也无法导出芯片内的密钥
└── 出发方向：软件存储密钥会被恶意程序读取；TPM 用"硬件隔离"把密钥锁进物理芯片，是移动设备/电脑的行业标准做法
```

```plain
HWID（Hardware Identifier，硬件标识）
├── 含义：由设备硬件特征（CPU 序列号、存储序列号等）派生的设备唯一标识
├── 原理：把密钥与"这台设备"绑定——换设备就失效，防止密钥被复制到其他机器
└── 出发方向：无 TPM 芯片的低成本设备（IoT 传感器等）需要替代方案，HWID 提供"软件层面的物理绑定"
```

**关键安全属性：**

- PSK 永不离开设备。它不会通过网络传输，不会存储在云端，不会备份到 SD 卡
- PSK 是长期密钥。它不像会话密钥那样每次通信后更换，而是设备的"根身份"
- **PSK 泄露 = 全崩。** 如果攻击者通过某种方式（如侧信道攻击、供应链植入）获取了你的 PSK，他可以冒充你参与任何会话。因此，PSK 的物理保护是最高优先级

> 【隐私风险】PSK 是"单点泄露即全局受损"的密钥材料：泄露后攻击者可冒充你的身份、解密（历史泄露范围内）的通信、参与任意会话。它也是供应链攻击（在硬件/软件出厂前植入后门）的主要目标。
>
> 【防护建议】① 只使用带 TPM 的设备（PSK 永不出芯片）——**注意：1.0.0 客户端不会把 PSK 写入芯片，也不会使用 TPM，该项需部署方自行落实**；② 定期检查设备固件来源，警惕来路不明的"预装软件"；③ 若怀疑 PSK 泄露，立即吊销旧令牌、申请新令牌、更换设备（PSK 与硬件绑定时换机即换钥）；④ 侧信道攻击（功耗分析、电磁泄漏）是物理接触场景的威胁，高安全场景应使用有屏蔽措施的设备。
>
> 【合规提示】PSK 属于"密钥材料"，按照密码管理最佳实践：密钥应分层管理（根密钥 / 会话密钥分离）、最小化使用范围（PSK 只参与派生，不直接加密数据）、建立密钥轮换与销毁机制。

> **常见误区**：PSK 是"预共享密钥"，但**不是口令/密码**。密码是人类可记忆的短字符串（可猜测、可爆破）；PSK 是 256 位真随机数（不可猜测、由硬件生成）。两者安全性天差地别，不要用"设置一个密码"的心态对待 PSK。

### 4.1.5 多令牌与多服务器策略

一台设备可以持有多个令牌，连接多个服务器：

1. **隔离性**：用 TCA-A 的令牌连接服务器 X，用 TCA-B 的令牌连接服务器 Y。即使服务器 X 被攻破，服务器 Y 的通信不受影响
2. **冗余性**：如果 TCA-A 被关闭，你可以立即切换到 TCA-B 的令牌，继续通信
3. **匿名性**：不同服务器看到你使用不同的令牌哈希，无法跨服务器关联你的身份

> **关联知识**：这像密码管理器中的"一网站一密码"策略——把信任分散到多个独立机构，任何单一机构的故障或背叛都只影响局部。

## 4.2 四阶段握手规范（标准流程）

在两个人开始秘密交谈之前，他们需要先确认彼此的身份，并协商一个共同的"暗号"——只有他们两人知道的加密密钥。这个过程就是"握手"。

```plain
握手（Handshake）
├── 含义：通信双方在正式传输数据之前，先完成身份确认和密钥协商的交互过程
├── 原理：用几轮"问答"交换必要信息（身份证明、公钥、随机数），双方各自独立计算出相同的会话密钥
└── 出发方向：没有握手就直接加密通信，双方没有共享密钥、也无法确认对方身份——握手是加密通信的"前置步骤"
```

在 ZT-DSP 中，握手分为四个阶段：

1. **身份宣告**——"我是谁，我要找谁"
2. **密钥同步**——"我们共同计算一个秘密密钥"
3. **锚点锁定**——"确认我们处于同一个会话中"
4. **加密传输**——"开始用密钥加密消息"

### 4.2.1 阶段一：身份宣告（入住登记）

**【场景】**：住客 A 来到酒店前台，出示两张门牌号：自己的门牌号 H(Token_A) 和要找的人的门牌号 H(Token_B)。

**【技术流程】**：客户端 A 向服务器 S 发送身份宣告（阶段一帧为**明文**——此时双方尚无共享会话密钥，该帧的安全性来自"接入随机数绑定 PSK"与后续阶段三的确认标签，而非加密），包含以下信息：

1. **源令牌哈希 H(Token_A)**：用于标识自己；在阶段一中以明文形式用于路由
2. **目标令牌哈希 H(Token_B)**：用于标识要找的人；服务器据此在等候池中查找匹配
3. **TCA 签名过的令牌本体**：证明 A 的身份是合法的；服务器验证签名有效性
4. **授权码（若服务器要求）**：证明 A 被允许进入这家特定的酒店
5. **能力标志**：声明 A 支持的模块与加密参数（如支持的加密算法与参数列表）
6. **接入随机数**：符合服务器库声明的参数（长度、速率、格式）；作为身份心跳，证明 A 是"活的"且持有正确的密钥材料

> **线上帧格式（与官方客户端逐字节核对）**：以上 6 项信息在网络上并不是"6 个独立字段"，而是装进一个阶段一帧（**完整逐字节布局、参数 JSON 的线上结构与校验规则、上限常量见附录 F.1；默认参数下该帧最小约 228 字节**）：

```plain
阶段一帧（线上格式）：
[param_len(4B)] [参数 JSON] [identity_len(4B)] [identity_blob] [nonce_len(4B)] [接入随机数]

字段映射：
• 参数 JSON（能力标志）→ "random_len"、"random_rate"、"window"、
  "key_len"、"hash"、"aead"、"module_flags"（JSON 键值对，长度上限 4096 字节）
• identity_blob（身份材料，上限 8192 字节）→ 默认内容 = 源令牌哈希(32B) ‖ 目标令牌哈希(32B)；
  若挂载了 TCA/授权模块，则由钩子替换为"TCA 签名令牌 + 授权码"等身份声明
• 接入随机数（nonce，上限 512 字节）→ 见下方公式；对端会校验其长度是否等于声明的 random_len
```

> **接入随机数的真实出身（易错点）**：一种常见误解是把接入随机数看成"派生自 PSK、TPM/HWID 和 TCA 令牌"，这与官方实现不符。官方客户端实际是：

```plain
接入随机数 = HKDF-SHA3-256(IKM = PSK, salt = 新鲜随机盐(32B), info = "ZT-DSP-PHASE1-NONCE-v3", 输出长度 = random_len 位)
```

| 元素 | 注释（输入/输出/作用） |
|------|------------------------|
| 接入随机数 | **输出**：长度 = random_len 位（默认 256 位）的"身份心跳" |
| HKDF-SHA3-256(...) | **函数**：密钥派生函数。IKM 相同、salt 不同 → 输出不同；但只有持有同一 PSK 的双方才能算出同一序列（确定性） |
| IKM = PSK | **输入**：设备专属密钥。只有持有正确 PSK 的客户端才能生成"看起来正确"的随机数，这是"证明我持有密钥"的暗号 |
| salt = 新鲜随机盐 | **输入**：每次握手新生成的随机盐，防止攻击者预计算（离线穷举）PSK 的派生结果 |
| info = "ZT-DSP-PHASE1-NONCE-v3" | **上下文串**：标识用途，防止与其他派生（MK/EK 等）产出相同的值 |

> **实践提示**：接入随机数**不是**纯随机数，而是"PSK 驱动的确定性随机数"——对端只校验它的长度等于声明的 random_len，**无法（也不试图）重算它**；"它是否由正确 PSK 派生"由阶段三确认标签间接体现（PSK 错 → MK 错 → 标签必错）。这就是它被称为"身份心跳"的原因：心跳的节奏只有持有同一 PSK 的人知道。

> **实践解读**：阶段一的核心逻辑是"**证明你持有合法身份，但绝不泄露身份秘密**"。A 出示的是令牌的**哈希**（门牌号）和 TCA 的**签名**（可公开验证），而不是令牌本身或 PSK——设想这样一个场景：就像住客给前台看身份证复印件和防伪水印，而不是交出身份证原件。（以上为设想，非技术描述）

> 【隐私风险】阶段一中，源/目标令牌哈希以**明文**传输，服务器（及沿途监控者）能看到"H(Token_A) 在找 H(Token_B)"。这意味着服务器知道"谁在找谁"的元数据——虽然不知道门牌号背后的真人是谁，但长期观察可建立设备行为画像。
>
> 【防护建议】① 令牌哈希可定期更换（换令牌）；② 多服务器场景使用不同令牌，避免跨服务器关联；③ 阶段四起令牌哈希改为加密传输（见 4.2.4），服务器只能看到路由所需的会话 ID。
>
> 【合规提示】"谁在找谁"属于通信元数据。按隐私保护原则，服务器运营者应**不记录、不存储**阶段一的配对信息（等候池 30 秒自动清除正是为此设计），并在隐私政策中明确声明。

**【服务器处理流程】：**

1. **参数核对**：检查接入随机数的长度、速率、格式是否符合库声明。不符合 → **静默丢弃（Silent Drop）**。不返回错误，不记录日志，不消耗计算资源。在攻击者的视角下，这个端口与关闭端口没有任何区别
2. **令牌验证**：验证 TCA 签名是否有效；查询 CRL（吊销列表），确认令牌未被吊销；若服务器要求授权码，验证授权码是否在白名单内
3. **等候池匹配**：查找等候池中是否有持有 H(Token_A) 的住客（即 B 已经先到，在等 A）。如果有 → 将 A 和 B 配对，送入同一房间；如果没有 → 将 A 放入等候池，等待 B 到来
4. **等候池管理**：等候池中的每一份登记表都独立存放，互不可见；等候项在 30 秒后自动清除（防止长期占用内存）；前台绝不会将 A 的登记信息广播给大厅里的其他人

> **实践提示（调参踩坑）**：初学者搭建服务器时最常见的错误是"参数没对齐"——客户端按默认参数发包，服务器按自定义库声明核对，结果所有包都被静默丢弃，表现为"连不上且没有任何报错"。排查方法：逐个对比双方库文件中的 **7 项匹配参数**——随机数长度（random_len）、生成速率（random_rate）、协商窗口（window）、密钥长度（key_len）、哈希算法（hash）、加密算法（aead）、模块标志（module_flags）——必须完全一致（官方客户端 `--version` 与启动时的参数打印可直接对照）。

### 4.2.2 阶段二：密钥同步（房间内对暗号）

**【场景】**：A 和 B 进入房间后，房间已经隔离。此时双方各自生成临时密钥对并交换公钥，完成"对暗号"过程。

**【技术流程】：**

**步骤 1：生成临时密钥对**

A 生成临时密钥对 (sk_A, pk_A)，B 生成临时密钥对 (sk_B, pk_B)。

```plain
密钥对（Key Pair）
├── 含义：一对数学上关联的密钥——私钥（secret key, sk）保密，公钥（public key, pk）公开
├── 原理：用私钥能算出公钥，但用公钥无法反推私钥；双方交换公钥后，各自用"自己的私钥 × 对方的公钥"能算出同一个共享秘密
└── 出发方向：对称加密需要"同一把钥匙"，但网络传输钥匙会被窃听；非对称密钥对让双方在不泄露私钥的情况下"各自算出同一把钥匙"
```

临时密钥对是"一次性的"。每次会话都会生成新的密钥对，会话结束后立即销毁（内存清零）。这与长期 PSK 不同——PSK 是设备的"根身份"，而临时密钥只是本次会话的"临时身份"。**为什么需要临时密钥？** 因为即使攻击者记录了你今天的所有通信，明天你的临时密钥已经更换，他无法解密明天的通信。这就是"前向安全"（Forward Secrecy）——长期密钥泄露不影响历史会话。

```plain
前向安全（Forward Secrecy，FS）
├── 含义：即使长期密钥（PSK）将来某天泄露，过去已发生的会话也无法被解密
├── 原理：每个会话使用独立的临时密钥派生会话密钥；会话结束临时私钥即销毁。攻击者事后拿到 PSK，也缺了"当时的临时私钥"这一环，算不出过去的会话密钥
└── 出发方向：长期密钥泄露是迟早可能发生的事（设备被攻破、机构被胁迫）；前向安全把损失限制在"泄露之后"，保护全部历史通信
```

> **生活类比**：设想这样一个场景：前向安全像"每次见面都换一把新锁"——即使某天你的万能钥匙（PSK）被偷了，小偷也只能开未来的门，打不开过去所有用旧锁的房间。
> （以上为设想，非技术描述）

**步骤 2：交换公钥**

A 和 B 通过服务器交换公钥 pk_A 和 pk_B。公钥可以公开传输，即使被截获也无妨；服务器只负责转发公钥，无法推导出共享秘密。

> **线上流程（与官方客户端核对）**：
>
> 1. 发起方 A 发送：`[pub_len(4B)] [pk_A(32B)] [session_salt(32B)]` —— 会话盐随 A 的公钥包一起发出
> 2. 响应方 B 收到后**先计算 DH**，再决定是否回应：若公钥长度异常或属于低阶点（如全零、u=1 等无效值），B 会**严格静默丢弃**——不发送任何字节、不主动关闭连接（客户端版本 1.0.0 起的安全加固，目的是防止"验证失败前已泄露响应帧"）
> 3. B 验证通过后才回送：`[pub_len(4B)] [pk_B(32B)]`（发起方帧共 68 字节、响应方帧共 36 字节；响应方"先算 DH 再回应"的顺序约束与帧布局细节见附录 F.3）
>
> **常见误区**：公钥是**公开**信息，可以放心交给服务器转发；但私钥（sk_A/sk_B）**绝不能**离开设备。设想这样一个场景：把公钥想象成"带锁的邮箱编号"——任何人都能往邮箱里投信（用公钥加密），但只有持钥匙的人（私钥）能开箱。（以上为设想，非技术描述）

**步骤 3：计算共享秘密**

- A 计算：DH = X25519(sk_A, pk_B)
- B 计算：DH = X25519(sk_B, pk_A)

数学保证：双方计算出的 DH 值完全相同。

```plain
DH（Diffie-Hellman，迪菲-赫尔曼密钥交换）
├── 含义：一种让双方在不安全信道上各自算出同一共享秘密的数学协议
├── 原理：利用"单向函数"（模幂运算/椭圆曲线标量乘法）：算出共享值是容易的，反推私钥是计算上不可行的。A 拿自己的私钥与 B 的公钥运算，B 拿自己的私钥与 A 的公钥运算，结果相同
└── 出发方向：最早解决"隔空传密"问题的方案（1976 年），是所有现代密钥交换的鼻祖。X25519 是其椭圆曲线现代版本
```

> **常见误区**：DH 交换本身**不防中间人**——攻击者可以分别与 A、B 各做一次 DH（"双人转圈"攻击）。ZT-DSP 防 MITM 靠两道关卡：**① PSK 参与派生**（步骤 4）——攻击者没有 PSK，即使完成 DH 也派生出错误的密钥；**② 阶段三确认标签交换**（4.2.3）——双方交换绑定全部握手材料的 HMAC 确认标签，任何一方的身份宣告被替换都会导致标签不匹配，握手立即失败。三层防护（PSK + DH + 盐）缺一不可。

**步骤 4：派生会话主密钥**

```
MK = HKDF-SHA3-256(IKM = PSK ‖ DH, salt = session_salt, info = "ZT-DSP-MK-v3", 输出 = 256 位)
```

| 行 | 代码元素 | 注释（输入/输出/作用） |
|----|----------|------------------------|
| 1 | `MK` | **输出**：会话主密钥（Master Key），256 位。后续所有密钥都从它派生，是本次会话的"总钥匙" |
| 1 | `HKDF-SHA3-256(...)` | **函数**：密钥派生函数（见 4.2.2）。把输入材料加工成合格的密钥 |
| 1 | `IKM = PSK ‖ DH` | **输入①**：PSK（双方共享的长期设备专属密钥，256 位）与 DH 结果（X25519 临时密钥交换产生的共享秘密，256 位）**拼接**成 IKM（Input Keying Material，输入密钥材料）。PSK 提供"身份锚定"——只有持有同一 PSK 的双方才能算出相同的 MK，这是防冒充的关键；DH 提供"会话独特性"——每次会话都不同，即使 PSK 泄露也无法解密历史会话（前向安全） |
| 1 | `salt = session_salt` | **输入②**：256 位随机数，由发起方生成，随公钥包明文发送。**注意：session_salt 是 HKDF 的盐（salt）参数，不是拼进 IKM 的密钥材料**。作用：提供"不可预测性"——防止攻击者预计算（离线穷举 PSK 派生结果） |
| 1 | `info = "ZT-DSP-MK-v3"` | **上下文串**：协议版本标识。防止不同协议版本/用途之间密钥混淆（如果两个协议用同样输入派生，会得到同样的密钥，这是危险的） |
| 1 | `输出 = 256 位` | **输出长度**：要求派生 256 位的密钥 |

> **常见误区（易错点）**：一种常见写法是把公式写成 `MK = HKDF(PSK ‖ DH ‖ session_salt)`，看起来三个输入"平等并列"。但官方实现（`cryptography` 库的 `HKDF` 类）把 `session_salt` 作为**独立的盐参数**传入（RFC 5869 的标准用法），IKM 只是 `PSK ‖ DH`。二者派生结果**完全不同**——按"三者并列"写法实现的客户端，与官方客户端握手必然失败（阶段三确认标签不匹配）。这也是"协议公开、实现自由"的反面教材：实现自由不等于可以随意改动公式细节，参数与公式必须与库声明一致。

> **实践解读（三元公式）**：为什么是三个输入而不是一个？历史教训告诉我们：只用 PSK（DRNG 路线）→ 泄露即全崩；只用 DH → 防不了冒充；只用盐 → 任何人都能算出。三者各司其职：**PSK 管"你是谁"（身份锚定，作为 IKM 的一部分），DH 管"这次会话独一份"（前向安全，IKM 的另一部分），盐管"猜不到"（作为 HKDF 的 salt 参数）**。缺任何一个，安全模型就崩。

**步骤 5：销毁临时私钥**

sk_A 和 sk_B 从内存中彻底清零，不再保留。临时私钥只存在于阶段二的短暂窗口内。即使攻击者在会话结束后立即攻破设备，也无法恢复已经销毁的临时私钥，因此无法重新计算 DH，无法解密历史通信。**这就是前向安全的工程实现。**

> **实践提示（实现要点）**：销毁不只是"置零"，还要防止编译器优化掉清零操作（优化器可能认为清零是无用代码而跳过）。实现时应使用专门的"安全清零"函数（如 `secure_zeroize`/`explicit_bzero` 类 API），并对密钥所在内存页加锁（mlock）防止被换页到磁盘。

### 4.2.3 阶段三：锚点锁定（确认房间唯一性）

**【场景】**：密钥派生完成后，双方需要确认"我们确实在同一个房间里"，防止中间人攻击或会话混淆。

**【技术流程】：**

**1. 计算锚点**

```
锚点 = HMAC-SHA3-256(MK, "ZT-DSP-ANCHOR-v3")
```

| 行 | 代码元素 | 注释（输入/输出/作用） |
|----|----------|------------------------|
| 1 | `锚点` | **输出**：256 位锚点值，本会话的"身份指纹"，用于绑定会话上下文 |
| 1 | `HMAC-SHA3-256(...)` | **函数**：带密钥的哈希运算（见 4.2.2）。与普通哈希的区别：需要密钥参与，没有密钥就算不出正确结果 |
| 1 | `MK` | **输入①**：步骤 4 派生的会话主密钥。只有算出相同 MK 的双方才能算出相同锚点 |
| 1 | `"ZT-DSP-ANCHOR-v3"` | **输入②**：上下文串，防止与其他用途的 HMAC 结果混淆 |

锚点的作用是：确保双方处于同一个会话上下文中；派生后续所有加密密钥；防止重放攻击（序列号与锚点绑定）。锚点是确定性派生结果——双方使用相同的 MK 和相同的消息字符串，必然计算出相同的锚点。

**2. 派生会话 ID（路由标识）**

```
会话 ID = HKDF-SHA3-256(IKM = 锚点, info = "ZT-DSP-SID-v3", 输出 256 位) 的前 32 字节
```

| 行 | 代码元素 | 注释（输入/输出/作用） |
|----|----------|------------------------|
| 1 | `会话 ID` | **输出**：32 字节的会话路由标识。阶段四数据包的**明文**头字段，服务器据此把包投递到正确的房间 |
| 1 | `HKDF-SHA3-256(...)` | **函数**：密钥派生函数，同上 |
| 1 | `IKM = 锚点` | **输入**：步骤 1 计算的锚点。双方算出相同锚点 → 必然得到相同会话 ID |
| 1 | `info = "ZT-DSP-SID-v3"` | **上下文串**：标识用途为"会话 ID"，防止与其他派生混淆 |
| 1 | `前 32 字节` | **截断**：派生 256 位后只取前 32 字节（会话 ID 字段长度） |

> **实践解读**：会话 ID 是**明文**的（服务器要读它才能路由），但它是从锚点确定性派生的——没有正确 MK 的攻击者伪造的会话 ID，在阶段四会被"会话 ID 不匹配"直接丢弃。这就是"路由信息可见但不可伪造"的设计。

**3. 派生会话加密密钥（区分收发方向）**

```
（发起方 A 视角）
EK_send = HKDF-SHA3-256(IKM = MK ‖ 锚点 ‖ 0x01, info = "ZT-DSP-EK-v3", 输出 256 位)
EK_recv = HKDF-SHA3-256(IKM = MK ‖ 锚点 ‖ 0x02, info = "ZT-DSP-EK-v3", 输出 256 位)

（响应方 B 视角：两个角色字节对调——B 的 EK_send 用 0x02、EK_recv 用 0x01）
```

| 行 | 代码元素 | 注释（输入/输出/作用） |
|----|----------|------------------------|
| 1 | `EK_send` | **输出**：本方向发送数据用的加密密钥（Encryption Key），256 位 |
| 1 | `EK_recv` | **输出**：接收对端数据用的加密密钥，256 位。发送用 EK_send、接收用 EK_recv，二者不同 |
| 1 | `HKDF(...)` | **函数**：密钥派生函数，同上 |
| 1 | `IKM = MK ‖ 锚点` | **输入**：主密钥拼接锚点。锚点的加入保证"每个会话的 EK 独一无二"——即使 MK 相同（理论场景），不同锚点也派生不同 EK |
| 1 | `0x01 / 0x02` | **角色字节**：发起方（Initiator）方向的 IKM 末尾追加 `0x01`，响应方（Responder）方向追加 `0x02`。作用：**区分收发两个方向的密钥**——A 的 EK_send 恰好等于 B 的 EK_recv，反之亦然；任何一方都无法用"自己的发送密钥"冒充对端 |
| 1 | `info = "ZT-DSP-EK-v3"` | **上下文串**：标识该密钥用途为"加密"，与锚点、认证等用途的密钥区分开 |

> **常见误区（易错点）**：一种常见写法是 `EK = HKDF(MK ‖ 锚点, ...)`——不分方向，仿佛双方共用同一把 EK。官方实现实际派生**两把**方向密钥，靠 IKM 末尾的角色字节（0x01/0x02）区分。这既是安全设计（防止"反射攻击"：把对方发给你的包原样弹回去），也是互操作细节：按不分方向的 EK 写法实现的客户端会因密钥不匹配而握手失败。

**4. 交换确认标签（锚点确认）**

密钥派生完成后，双方还要互相证明"我们的握手材料完全一致"——包括双方的身份宣告、参数 JSON、会话盐和公钥。这个"完整对话记录"叫 **transcript（对话抄本）**：

```
transcript = 双方阶段一原始帧（发起方优先）‖ session_salt ‖ 双方临时公钥（发起方优先）

发起方发送：确认标签_A = HMAC-SHA3-256(MK, "ZT-DSP-CONFIRM-INIT-v3" ‖ transcript)
响应方发送：确认标签_B = HMAC-SHA3-256(MK, "ZT-DSP-CONFIRM-RESP-v3" ‖ transcript)
```

| 行 | 代码元素 | 注释（输入/输出/作用） |
|----|----------|------------------------|
| 1 | `transcript` | **输入①**：把双方交换过的所有握手材料按固定顺序拼接：双方阶段一原始帧（发起方在前）→ 会话盐 → 双方临时公钥（发起方在前）。任何一方身份宣告、参数、公钥被替换，transcript 就变了 |
| 1 | `HMAC-SHA3-256(MK, ...)` | **函数**：带密钥的哈希运算。只有持有相同 MK 的双方才能算出相同的确认标签 |
| 1 | `"ZT-DSP-CONFIRM-INIT-v3"` / `"ZT-DSP-CONFIRM-RESP-v3"` | **上下文串**：区分发起方与响应方的标签用途，防止"反射攻击"（把对端发的标签原样弹回去冒充自己） |
| 1 | `确认标签` | **输出**：32 字节 HMAC 标签。双方各发一个、各验证一个：发起方验证 B 的标签，响应方验证 A 的标签 |

交换顺序（按官方实现）：发起方先发自己的标签 → 响应方读取（帧级错误——读取失败/长度异常/超时——才静默丢弃）→ 响应方发送自己的标签 → **双方各自**以恒定时间比较对方的标签，不匹配 → 擦除全部密钥并报"锚点确认失败：PSK 不匹配、角色不匹配或反射/中间人攻击"。注意：标签**内容**的校验发生在双方交换完成之后，不是"响应方验证通过才发"——这与阶段一/二"先验证后回应"的次序不同（精确时序见附录 F.4 与附录 H）。

> **实践解读**：确认标签是整场握手的"期末考试"——前面所有步骤（阶段一的身份宣告、阶段二的公钥与 DH）无论哪一步被篡改或算错，最后的标签必然对不上，握手直接失败。这也就是 4.2.2 中"PSK 防冒充"真正落地的地方：攻击者没有 PSK，就算完成 DH 也派生出错误的 MK，标签校验必败。

**5. 初始化序列号**

初始序列号 = 0（双方同步归零）。序列号从 0 开始，每发送一个数据包递增 1。接收方只接受序列号大于上次接收值的包，防止重放攻击。

> **实践提示**：序列号是 64 位（8 字节）整数，按每秒 1024 个包（`random_rate` 默认值）计算，约需 5.7 亿年才会溢出——但在实现中仍必须处理「会话重启后序列号归零」与「乱序包到达」这两种边界情况。**本协议采用严格单调判定，禁止滑动窗口**：接收方只接受 `seq > seq_recv`（`seq_recv` 初始为 −1），任何 `seq <= seq_recv` 的包一律按重放/乱序处置——丢弃该包、擦除全部密钥并终止会话（见 4.2.4 与附录 F.5）。**原因**：阶段四的 nonce 由「固定 4 字节前缀 ‖ seq」直接构成，一旦用滑动窗口容忍乱序，就等于在同一密钥下复用 nonce，AEAD 的机密性与完整性会同时失效。

```plain
重放攻击（Replay Attack）
├── 含义：攻击者把截获的合法数据包，原样重新发送给接收方，试图让接收方重复处理（如重复扣款、重复指令）
├── 原理：如果接收方无法区分"新消息"和"旧消息重发"，就会重复执行。序列号（单调递增）是经典防御：重发的旧包序列号 ≤ 已收最大值，直接丢弃
└── 出发方向：网络攻击者天然具备"记录和重放"能力，任何无状态验证的协议都面临此威胁
```

**6. 擦除根密钥材料（补充）**

确认标签验证通过、握手宣告完成之后，**MK、锚点、PSK 全部从内存中清零**（官方客户端在阶段三结束时执行 `secure_zero` 擦除）。此后整个会话只保留：EK_send / EK_recv（数据加密用）、会话 ID（路由用）、序列号（防重放用）。

> **实践解读**：为什么用完就擦？这是"最小暴露面"原则：PSK 和 MK 只在握手阶段需要，越早销毁，被攻破设备上残留的密钥材料就越少。攻击者即使此刻攻破设备，也拿不到 PSK 和 MK——只能拿到本会话的 EK，且 EK 还会被持续锁定不断更换（4.2.5）。

### 4.2.4 阶段四：加密数据传输（箱子投递）

**【场景】**：完成前三阶段后，A 和 B 开始交换箱子（加密数据包）。每个箱子都上了锁，前台只能看到外观，无法打开。

**【数据包结构（完整字段）】：**

> **线上布局（与官方实现逐字节核对）**：一个阶段四数据包由"明文头 + GCM 密文"两部分组成，密文内部再装 7 个字段（**带偏移的逐字节布局表、接收校验流水线的固定顺序、心跳包 165 字节实测尺寸见附录 F.5；随机填充与 fmt 标记的精确编码见附录 G**）：

```plain
线上数据包（加密后）：
[会话 ID(32B, 明文)] [序列号(8B, 明文)] [密文长度(4B, 明文)] [GCM 密文(可变) + 认证标签(16B)]

明文载荷（加密前，即 GCM 密文的内容）：
[时间戳(8B)] [载荷格式标记 fmt(1B)] [目标令牌哈希(32B)] [源令牌哈希(32B)]
[用户明文(可变)] [随机填充(0~2048B，仅 fmt=0x01 时存在)] [填充长度(2B，仅 fmt=0x01 时存在)] [next_seed(32B)]
```

| 字段名称 | 长度 | 加密 | 说明 |
|----------|------|------|------|
| 目标令牌哈希 | 32B | 是 | 使用会话密钥 EK 加密，防止明文身份关联。服务器看到加密后的目标哈希，无法知道这条消息发给谁 |
| 源令牌哈希 | 32B | 是 | 同上。加密后防止流量分析者通过源目标关联建立社交图谱 |
| 时间戳 | 8B | 是 | 毫秒级 Unix 时间戳（uint64 大端）。接收方校验 `‖当前时间 − 时间戳‖ ≤ 时间戳窗口`（默认 30 秒），防重放与延迟截送 |
| 载荷格式标记 fmt | 1B | 是 | `0x00` = 无随机填充（默认）、`0x01` = 带随机填充。接收方按此标记剥离填充；官方客户端可单边启用填充，无需双方协商 |
| 随机填充 | 0~2048B | 是 | 参考建议 512~2048B。填充消除长度指纹，使所有包大小相近。官方客户端默认关闭（`--padding-min/max` 启用） |
| 预密钥种子 next_seed | 32B | 是 | 下一包的棘轮种子：`new_EK = HKDF-SHA3-256(IKM = 当前EK ‖ next_seed, info = "ZT-DSP-EK-ROTATE", 输出 256 位)`（持续锁定，见 4.2.5） |
| 用户明文 | 可变 | 是 | 实际消息内容（含心跳空包：明文长度 0） |
| 会话 ID | 32B | 否 | 明文路由字段，派生自锚点。服务器根据会话 ID 将包投递到正确的房间 |
| 序列号 | 8B | 否 | 明文；64 位单调递增，防重放攻击。接收方检查序列号大于上次接收值，否则丢弃 |
| 密文长度 | 4B | 否 | 明文长度字段，接收方先读它再读密文 |
| GCM 认证标签 | 16B | 否 | AES-256-GCM 自动附带的认证标签。**认证范围 = AAD + 全部密文**；篡改任何字段都会导致验证失败 |

> **两个关键构造（补充，实现者必读）**：
>
> - **AAD（附加认证数据，不加密但参与认证）**：`AAD = 会话 ID ‖ 序列号(8B 大端)`，共 40 字节。服务器必须能读会话 ID 和序列号来路由与过滤，但又不能让攻击者篡改它们——AAD 正好满足"可见且防篡改"。AAD 不含任何版本串。
> - **GCM nonce（一次性数）**：`nonce = 0x00000000(4B) ‖ 序列号(8B 大端)`，共 12 字节。序列号单调递增 → 每个包 nonce 唯一，满足"同一密钥下 nonce 绝不重用"的硬性要求。

```plain
AES-256-GCM（Advanced Encryption Standard 256 + Galois/Counter Mode）
├── 含义：对称加密算法（AES，256 位密钥）搭配认证加密模式（GCM），一条算法同时提供"加密"和"完整性认证"
├── 原理：AES 负责把明文变成密文（机密性）；GCM 模式生成认证标签（类似"防伪码"），任何一位数据被篡改，标签校验即失败（完整性 + 真实性）
└── 出发方向：只加密不认证会被"密文翻转"攻击篡改内容；GCM 把加密与认证合二为一，性能好（可并行）、安全强，是现代通信的事实标准
```

```plain
IV（Initialization Vector，初始化向量）/ Nonce（一次性数）
├── 含义：加密时引入的一段随机数，让"相同的明文"加密出"不同的密文"
├── 原理：密码学要求同一密钥下，每个加密操作使用不同的 IV；否则相同明文产生相同密文，攻击者可据此推断内容模式
└── 出发方向：没有 IV，加密会退化成"可猜测的替换表"。GCM 的 IV 唯一性至关重要——重复使用 IV 会直接摧毁 GCM 的安全性
```

```plain
AAD（Additional Authenticated Data，附加认证数据）
├── 含义：不加密但参与认证的数据——接收方验证其完整性，但内容公开可见
├── 原理：GCM 对"密文 + AAD"一起计算认证标签；AAD 被篡改，标签校验失败
└── 出发方向：路由字段（会话 ID、序列号）必须让服务器可见才能转发，但又必须防篡改——AAD 正好满足"可见且防篡改"的双重需求
```

> **常见误区**：GCM 的"认证"不等于"签名"。GCM 认证标签证明"数据没被篡改且确实由持有 EK 的一方发送"，但它不能向第三方证明发送者身份（那是 Ed25519 签名的职责）。两种机制用途不同，不要混用。

> 【隐私风险】尽管载荷已加密，但**流量模式仍可泄露信息**：包大小（已被填充缓解）、发送频率、会话时长、连接关系（服务器仍知道"会话 ID X 与 Y 在通信"）。这就是为什么协议强调随机填充 + 时序抖动（5.4 节）。
>
> 【防护建议】① 使用随机填充（512~2048B）抹平长度指纹；② 高安全场景启用发送时序抖动（附录 G.3）；③ 会话 ID 定期轮换（通过持续锁定跳转），缩短可关联窗口。
>
> 【合规提示】端到端加密（E2EE）下，服务器不接触明文，这本身就是最强的隐私保护实践。但运营者仍应遵守元数据最小化原则：不记录会话时长、流量大小等可关联数据。

**【发送流程】：**

1. A 使用 EK_send 加密载荷（消息内容），生成 GCM 密文和认证标签
2. A 将目标令牌哈希、源令牌哈希、时间戳、fmt 标记、next_seed 一并装入明文载荷（防止明文暴露身份）
3. A 将整个数据包通过服务器转发给 B
4. 服务器只负责投递，不打开箱子

> **实践细节（"先消耗状态，后尝试发送"）**：官方客户端在**发送前**先完成三件事：① 生成新的 next_seed 并派生下一包密钥 `new_EK = HKDF(当前EK ‖ next_seed, "ZT-DSP-EK-ROTATE")`；② 把内存中的当前 EK 清零、换成 new_EK；③ 序列号 +1。然后才加密发送当前包。这意味着：即使发送失败（断网、被掐断），密钥也已经旋转过了——攻击者无法利用"发送失败导致密钥未旋转"来重放旧包。代价是发送失败后会话不可恢复，只能重连（官方客户端会提示"会话已不可逆失步"）。

**【接收流程】：**

1. B 收到数据包后，先检查**序列号**是否严格大于上次接收值（`seq > seq_recv`，`seq_recv` 初始为 −1），不满足 → **丢弃该包、擦除全部密钥并终止会话**（重放攻击或乱序旧包）
2. B 再检查**会话 ID**是否与当前会话匹配，不匹配 → **丢弃该包并终止会话**（串频或旧会话残留包）
3. B 验证 **GCM 认证标签**，失败 → **丢弃该包并终止会话**（数据被篡改或密钥不匹配）
4. B 解密载荷后，再做**三重内部校验**：① 载荷结构长度是否自洽（防越界）；② 载荷格式标记是否合法（未知 fmt）；③ **令牌哈希双向校验**——包内目标令牌哈希必须等于本地身份、源令牌哈希必须等于对端身份（防流量返送/串频/身份伪造）。以上任一项不通过 → **丢弃该包并终止会话**
5. B 校验时间戳：`|当前时间 − 时间戳| > 时间戳窗口`（默认 30 秒）→ 该包**已通过 GCM 认证但超窗口**，此时**只丢弃明文、仍旋转 EK 并推进序列号**（防止发送方已旋转、接收方未旋转导致会话永久失步）——**这是唯一不终止会话的失败分支**
6. B 正常获得明文消息。明文长度为 0 的包是**心跳包**，接收方静默跳过（官方客户端每 30 秒发一个，用于检测半开连接）

> **实践提示（接收顺序与失败策略都很重要）**：务必按「序列号 → 会话 ID → 认证标签 → 解密与内部校验 → 时间戳」的顺序处理。这个顺序本身是安全设计：先做廉价过滤（序列号/会话 ID），再做昂贵的密码学验证（GCM），最后才解密——既能防 DoS（垃圾包不触发解密），又能防信息泄露（不暴露"为什么丢"）。**除第 5 步时间戳超窗外，任何校验失败都必须"静默终止"**：丢弃该包、擦除全部密钥、结束会话，且不向对端返回任何错误码——这与附录 F.5 的终止策略、以及参考实现的 `session.py` 行为完全一致。

### 4.2.5 持续锁定与前向安全

在第四阶段，每个加密数据包除了承载消息外，还额外携带一个"预密钥种子"：

- 当前包：加密消息 + "下一包的密钥种子"
- 下一包：使用上一包预告的种子派生新 EK，再携带下下一包的种子

官方客户端的棘轮旋转公式（每包一次）：

```plain
new_EK = HKDF-SHA3-256(IKM = 当前EK ‖ next_seed, info = "ZT-DSP-EK-ROTATE", 输出 = 256 位)
```

| 元素 | 注释（输入/输出/作用） |
|------|------------------------|
| new_EK | **输出**：下一包的加密密钥，替代当前 EK（当前 EK 随即清零） |
| 当前EK ‖ next_seed | **输入**：当前密钥拼接本包携带的 32 字节预密钥种子。种子由发送方每次新生成（真随机），因此下一包密钥不可预测 |
| info = "ZT-DSP-EK-ROTATE" | **上下文串**：与"ZT-DSP-EK-v3"区分——后者派生初始 EK，前者做每包旋转 |

这个过程就是**持续锁定**：

- 攻击者即使截获了第 N 个包，也无法解密第 N+1 个包（密钥已变）
- 双方通过预密钥不断"跳频道"，形成前向安全链
- 虚拟房间确保这个跳转过程不被外部连接打断
- 子频道允许多个独立的前向安全链在同一房间内并行存在

> **实践提示（保活与失步）**：官方客户端每 30 秒发送一个**空载荷心跳包**（明文长度 0），专门用于检测"半开连接"（一方已掉线，但 TCP 连接因未发送数据而未被察觉）。心跳包同样参与棘轮旋转——即使没有消息，密钥链也在持续前进。这也是为什么"超窗口包仍要旋转 EK 并推进序列号"（4.2.4 接收流程第 5 步）如此重要：发送方的心跳包如果因时间戳超窗口被整体丢弃而不旋转，双方棘轮就会失步，后续所有包都无法解密。

> **关联知识**：持续锁定与 Signal 协议（WhatsApp/Signal 的加密基础）的"双棘轮"（Double Ratchet）思想同源——都是"每发一条消息就换一次密钥"。区别在于 ZT-DSP 的跳转完全在双方内部完成（预密钥种子随包传递），不依赖任何服务器逻辑。

## 4.3 静默丢弃机制

静默丢弃（Silent Drop）是 ZT-DSP 对抗架构的核心。设想这样一个场景：攻击者在扫描互联网，寻找 ZT-DSP 服务器。他向目标端口发送各种探测包：1 字节的垃圾数据、32 字节的随机数据、128 字节的伪造数据。（以上为设想，非技术描述）

如果服务器对每种错误都返回不同的错误码（如"长度错误"、"格式错误"、"签名无效"），攻击者就可以通过错误码的差异来推断："这个端口在运行 ZT-DSP，而且它的参数是这样的……"

**静默丢弃消除了这种信息泄露。** 无论攻击者发送什么，服务器都表现得像一个"关闭的端口"——没有任何响应。这使得大规模协议探测变得极其困难。

> **生活类比**：设想这样一个场景：静默丢弃像一扇"不透光的门"——敲门的人只能得到"无声"，无法从回应中判断门后是空房间、有保险库还是有一整队保安。而普通协议的门会通过"吱呀声"（错误码）暴露内部构造。
> （以上为设想，非技术描述）

> **实践提示（实现陷阱）**：静默丢弃的"静默"必须贯彻到底——① 不返回任何网络响应；② 不记录日志（日志本身就是给攻击者的反馈，也会让服务器成为取证目标）；③ 丢弃前不执行任何昂贵操作（直接在最外层参数核对处丢弃，防 DoS 放大）；④ 丢弃路径与正常路径在时序上尽量一致（避免攻击者通过"响应时间差异"推断"这确实是个 ZT-DSP 服务器"）。

> **常见误区**：静默丢弃 ≠ "不设防"。它是"防探测"层，不是"防攻击"层——合法包通过参数核对后仍要经过签名验证、CRL 查询、GCM 校验等完整防线。只靠静默丢弃而不实现验证逻辑的服务器，会被持有合法令牌的恶意客户端轻松攻破。

> **补充**：本节讲的是静默丢弃的**思想**。Responder 侧"严格静默"的**行为契约**——哪些失败必须静默（触发点全表）、静默期间"不发送、不关闭、挂起吞字节"的精确语义、发起方为何不对称——见**附录 F.2**；各阶段失败路径的完整矩阵见**附录 H.4**。

## 5.1 服务器不可信场景

**威胁**：服务器运营者试图窥探用户通信内容。

**防御**：

- **端到端加密**：服务器只能看到加密后的数据包，无法解密

```plain
端到端加密（End-to-End Encryption，E2EE）
├── 含义：数据只在发送端加密、接收端解密，中间所有环节（服务器、运营商）只能看到密文
├── 原理：加密密钥只在两端派生（第四册阶段二/三），服务器从未持有任何密钥材料
└── 出发方向：服务器被攻破、被胁迫、内部作恶都是真实威胁；E2EE 让服务器"想看也看不到"
```

- **服务器层加密**：默认取消服务器层加密，或采用 TLS 1.3/WireGuard 隧道（服务器不持有隧道密钥）

```plain
TLS 1.3（Transport Layer Security，传输层安全协议 1.3 版）
├── 含义：HTTPS 的加密基础，保护"客户端—服务器"这段链路的传输安全
├── 原理：客户端与服务器先握手协商密钥（证书验证 + 密钥交换），之后所有流量加密传输
└── 出发方向：防止传输途中的窃听与篡改（Wi-Fi 钓鱼、运营商劫持）。注意：TLS 保护的是"链路"（你到服务器），E2EE 保护的是"端到端"（你到对方），两者层次不同、可叠加
```

```plain
WireGuard（一种现代 VPN 隧道协议）
├── 含义：轻量、快速的加密隧道协议，常用于把多台设备组成私有网络
├── 原理：基于 Curve25519 密钥交换 + ChaCha20 加密，配置简单（一个公钥即一个节点身份）
└── 出发方向：替代老旧的 IPsec/OpenVPN——代码少、审计容易、性能高，成为 VPN 事实新标准
```

- **令牌哈希加密**：阶段四及之后，令牌哈希使用会话密钥加密，服务器无法关联长期身份

**服务器能做的最坏事情**：拒绝转发（断网）、延迟转发（降速）、丢弃特定会话的包——均为可用性攻击，但无法窃取内容。

**服务器无法做到的事情**：解密任何数据包（没有 PSK，没有会话密钥）；冒充住客（没有令牌私钥，没有授权码）；关联跨会话身份（令牌哈希已加密，会话密钥每次更换）。

> 【隐私风险】服务器虽然解不开内容，但**仍掌握通信元数据**：会话 ID 之间的对应关系、流量大小与频率、连接时长。在极端监控场景下，元数据足以描绘"谁在何时与谁通信"的社交图谱（即使不知道说了什么）。
>
> 【防护建议】① 服务器运营者主动"不记录"；② 用户侧通过多服务器分散打散关联性；③ 会话时长敏感场景可定时重连（切断可关联的连续会话）。
>
> 【合规提示】服务器运营者处于"数据处理者"位置：即使技术上无法解密内容，也应遵守元数据最小化原则，并公开隐私政策声明"记录什么、不记录什么"。

## 5.2 客户端不可信场景

**威胁**：恶意客户端试图接入网络、发起攻击或窃取信息。

**防御**：

- 令牌签名验证：无有效 Ed25519 签名的令牌无法通过阶段一
- 授权码白名单：无授权码的客户端无法进入要求授权码的服务器
- PSK 验证：即使进入房间，无 PSK 无法完成 X25519 后的 HKDF 派生
- 序列号与锚点：恶意客户端无法预测合法会话的序列号和密钥

> **实践解读**：这一节的防御是**分层**的——签名验证拦"无证者"，授权码拦"无门禁者"，PSK 拦"冒充者"，序列号拦"重放者"。每一层都独立工作，攻破一层还有下一层。这就是"纵深防御"（Defense in Depth）思想：不把安全押在单一机制上。

## 5.3 TCA 不可信场景

**威胁**：TCA 私钥泄露、被胁迫签发伪造令牌、或被政府关闭。

**防御**：

- 多 TCA 联邦：单 TCA 叛变不会摧毁整个生态，用户可切换到其他 TCA
- 快速冻结：系统支持冻结被攻破 TCA 的公钥，使其签名失效
- 历史会话不受影响：X25519 提供前向安全，已建立会话的密钥不依赖 TCA
- 设备多令牌：用户可持有多个 TCA 的令牌，降低单点依赖

> **生活类比**：设想这样一个场景：多 TCA 联邦像"多国护照"——一个国家作废你的护照，你还有别的国家的护照可用；服务器运营者像"多国边境检查"——不认可 A 国护照的酒店，可能认可 B 国护照。
> （以上为设想，非技术描述）

## 5.4 全链路主动对抗场景（分层攻击（九层威胁））

**威胁模型（分层攻击（九层威胁））：**

1. **信息截流**：攻击者截获所有网络流量
2. **二次重放**：攻击者重复发送合法数据包
3. **环境模拟**：攻击者伪造服务器、客户端或 TCA
4. **流量返送**：攻击者将数据包反射回发送端
5. **流量监控**：攻击者分析流量模式、时序、大小
6. **流量加密返送**：攻击者将截获的加密流量重新发送，测试反应
7. **流量混乱打包**：攻击者破坏包结构，注入垃圾数据
8. **随机流量杀死**：攻击者随机丢弃数据包
9. **随机流量延迟截送**：攻击者延迟数据包到达时间

```plain
流量分析（Traffic Analysis）
├── 含义：不破解加密内容，只通过观察流量特征（大小、时序、方向、频率）推断通信行为
├── 原理：即使内容加密，元数据依然外露；例如"深夜每小时精确发送 1KB 包"本身就泄露了行为模式
└── 出发方向：这是加密时代最主要的监控手段——攻击者不必解密，模式本身就够用了；防御手段是"抹平特征"（填充、抖动、噪声）
```

**防御矩阵：**

| 攻击手段 | 防御机制 |
|----------|----------|
| 信息截流 | 端到端 X25519+AES-GCM，截流者无法解密 |
| 二次重放 | 64 位递增序列号 + 时间戳窗口；重放包的序列号 ≤ 已接收最大值 → 丢弃该包、擦除全部密钥并终止会话 |
| 环境模拟 | PSK 验证 + Ed25519 签名 + 静默丢弃；无 PSK = 无法生成正确随机数/信标 |
| 流量返送 | 会话 ID 绑定 + 源目标令牌哈希校验；回环包的目标哈希与接收方身份不匹配 → 丢弃该包并终止会话 |
| 流量监控 | 随机填充（512~2048B）+ 时序抖动，消除长度指纹和时序指纹 |
| 流量加密返送 | GCM tag 验证失败 → 静默终止（丢弃该包、擦除全部密钥、结束会话） |
| 流量混乱打包 | 长度检查 → 静默终止；GCM 验证失败 → 静默终止（均为丢弃该包并结束会话） |
| 随机流量杀死 | 单一路径依赖，可能中断（可用多服务器分散缓解） |
| 随机流量延迟截送 | 时间戳 + 序列号 + 预密钥跳转；超窗口包只丢弃明文、不终止会话 |

> **实践解读（从表中能学到什么）**：注意防御机制几乎全部是"**验证不合格就不跟攻击者对话**"——协议只做检查，不合格就静默处理，绝不返回错误码。需要区分两层：**会话建立前的失败**（PSK/签名/格式）是真·静默丢弃；**会话建立后的失败**（序列号/会话 ID/GCM/令牌哈希）则按附录 F.5 静默终止（丢弃该包、擦除密钥并结束会话）。这种"少说多做"的风格贯穿整个协议：每个防御机制都在减少攻击者可利用的信息（时间信息、错误信息、长度信息）。填充与抖动两项防御的**精确线上编码**（fmt 标记、pad_len 字段位置、单边启用语义）见附录 G。

## 5.5 安全承诺与边界

在以上分层攻击（九层威胁）下，ZT-DSP 可以保证：

- **保证** — **机密性**：攻击者无法解密通信内容（除非 PSK 泄露）
- **保证** — **完整性**：攻击者无法篡改数据而不被发现
- **有条件** — **可用性**：在极端攻击下，通信可能中断
- **不保证** — **匿名性（绝对）**：如果攻击者监控全局并关联多载体，可能降低匿名性

**绝对的安全不存在。** ZT-DSP 的目标是：在密码学层面不可突破，在工程层面尽可能具备韧性（resilient，即遭遇攻击后能恢复、能降级生存的能力），在极端场景下维持最低限度生存。

> **常见误区（全文最重要的一条）**：**匿名 ≠ 加密。** ZT-DSP 保证的是"内容不被解密、身份不被冒用"，但它**不保证**"你这个人不被发现"。攻击者通过流量分析、物理定位、行为模式依然可能缩小你的范围。此外，密码学安全 ≠ 操作安全（OPSEC）——你用再强的加密，如果设备上装了间谍软件、或者你自己泄露了门牌号，一样不安全。
>
> 【隐私风险】威胁模型的边界：本协议不防"物理接触攻击"（设备被没收后的取证）、不防"侧信道攻击"（功耗/电磁分析）、不防"社交工程"（骗你交出令牌/门牌号）。
>
> 【防护建议】高威胁场景下的完整防护 = 协议加密（本协议）+ 设备物理安全（TPM、全盘加密）+ 操作纪律（OPSEC、不在不安全设备上使用）。任何单一环节的缺失都会拉低整体安全水平。

# 第八册：FAQ 与常见误区

> **【本册导读】** 本册收集初学者最常问的 15 个问题。每一个问题都标注了它对应的技术要点和常见误区，是"速查手册"性质的一册。
>
> **【初学者关注点】** 建议在读完第三册后通读一遍本册——它能验证你的理解是否到位（每个问题你都能在第三/四册找到对应章节）。

## Q1：我没有门牌号，怎么进酒店找人？这不是死循环吗？

**A：不是死循环。** 门牌号不是到酒店才领的，而是你进门之前就带在身上的。在 ZT-DSP 中，门牌号（令牌哈希）通过带外渠道获得：二维码扫描、加密邮件、线下见面、P2P 直连等。如果你没带门牌号，酒店前台不会告诉你任何人的房间号——这不是 bug，这是匿名性的底线。

流程是：① 出门前通过带外渠道获取对方的门牌号 H(Token_B) → ② 到酒店向前台出示自己的门牌号 H(Token_A) 和对方的门牌号 H(Token_B) → ③ 前台核对匹配，送入同一房间。

> **常见误区**："没有门牌号就进不了门" ≠ 协议有缺陷。设想这样一个场景：这就像"没有地址就寄不了信"——不是邮局的问题，而是通信的本质要求。ZT-DSP 明确不做"陌生人发现"（Q4），这是特性不是 bug。（以上为设想，非技术描述）

## Q2：那我的门牌号从哪来？TCA 到底是干嘛的？

**A：TCA（保安）不是帮你找人的，是给你发身份证的。**

- TCA = 身份制造厂：它验证你的设备后，签发一张令牌（内含随机种子 + Ed25519 签名）
- 门牌号 = 身份证的哈希：你把身份证复印一份（SHA-3-256），得到门牌号，用于在酒店找人
- 令牌存储：你的原始身份证（令牌）按协议设计应被安全地保存在设备的 TPM/HWID 中，不可导出、不可复制（**1.0.0 未实现硬件存储**）

关键点：一个设备可以持有多个 TCA 签发的多张身份证（多令牌）；TCA 只负责"这人有没有合法身份证"，不负责"这人要找谁"；找人是你自己的事。

## Q3：为什么要有 TCA？这不是中心化吗？

**A：TCA 不是中心化权威，而是社交共识。**

任何人可以自建 TCA，为小圈子签发令牌。TCA 的权威性取决于有多少人认可并加入。一台设备可以持有多个 TCA 的令牌，一台服务器可以持有多个 TCA 的白名单。

如果没有 TCA 的存在，无政府客户端将会摧毁整个协议生态：任何人都可以无限生成身份，发起垃圾连接、DDoS 攻击，公益服务器将在数小时内崩溃。**TCA 的存在是合理管控用户，同时保持匿名。** 你并不需要执着于一个 TCA 机构。

> **常见误区**：TCA ≠ 中心服务器。TCA 只做"签发+吊销"，不参与通信、不持有密钥、不在数据传输路径上。设想这样一个场景：把它类比成"护照签发国"更准确——护照国知道你有护照，但不知道你拿着护照去了哪里、见了谁。（以上为设想，非技术描述）

## Q4：如果我和朋友从来没见过面，也没法带外交换门牌号，还能用 ZT-DSP 吗？

**A：不能直接连接。** ZT-DSP 的核心设计是"无预设信任，不预设连接"——如果你不知道对方的门牌号，协议不会帮你"发现"他。

替代方案：通过可信中介（共同朋友）转发门牌号；通过公开公告板发布门牌号，等待对方主动联系；使用支持群组发现的第三方应用层协议，在其上建立初始信任后，再下沉到 ZT-DSP 进行加密通信。

**ZT-DSP 是管道，不是黄页。** 它负责让已知彼此的人安全通信，不负责让陌生人互相发现。

## Q5：服务器能看到我在哪个子频道说话吗？

**A：不能。** 服务器（前台）只能看到你进入了哪个房间（基于门牌号哈希匹配）和你在发送数据包（箱子）。但箱子是加密的（AES-256-GCM），服务器打不开；子频道的会话密钥是在房间内由客户端独立派生的，服务器不参与；子频道的创建/销毁指令本身也是加密的。

服务器知道"这个房间里有设备在通信"，但不知道"他们在哪个子频道、说了什么"。

> **关联知识**：这体现了"最小信息"设计——服务器只拿到路由所需的最小信息（房间号），拿不到内容（加密）、拿不到子结构（子频道）。与 5.1 节的元数据讨论呼应。

## Q6：既要匿名，又要有 TCA 来"管理"，这两者是否矛盾？

**A：匿名和管理不是对立的，是分层隔离的。**

| 层面 | 谁认识你 | 认识多少 |
|------|----------|----------|
| TCA（保安） | 认识你 | 只知道你的设备有合法身份证，不知道你要找谁、说了什么 |
| 服务器（前台） | 不认识你 | 只认门牌号哈希，不认证件背后的真人身份 |
| 通信对端 | 认识你 | 只有他知道门牌号对应的是你（因为你们带外交换过） |

TCA 的存在是为了防止无政府滥用。有了 TCA，服务器可以通过白名单过滤掉"没有合法身份证的住客"，保护公益资源。但你始终可以选择：使用多个 TCA 不锁定于单一机构；使用 P2P 模式完全不经过 TCA 和服务器。

> **常见误区**："匿名" ≠ "没有任何人知道你的任何信息"。ZT-DSP 的匿名是**分层匿名**：每层只知道完成自己职能所需的最小信息（见上表）。绝对的、无条件的匿名在现实世界中不存在（见 5.5）。

## Q7：什么是虚拟房间？

**A：虚拟房间是"持续锁定"状态的防护罩。** 当 A 和 B 进入第四阶段（加密数据传输）后，双方会开启持续锁定——不断通过数据包内的"下一个预密钥"跳转到新的加密上下文，防止外部追踪。

在这个过程中，服务器会为这对设备维持一个房间占位；如果有第三方 C 也持有相同的门牌号哈希（罕见但可能），试图加入这个房间，服务器会直接拦截并丢弃该请求。这个被保护的占位空间就是虚拟房间——它存在，但对外不可见、不可进入。

## Q8：什么是子频道？

**A：子频道是房间内的"临时群聊"。** 一个房间（匹配池）里，A 和 B 建立了一对一连接，但双方可以协商开启子频道，邀请更多持有相同门牌号前缀或衍生令牌的设备加入。每个子频道有独立的会话密钥（EK）、序列号空间、锚点派生路径。

关键特性：内容不保存（所有数据仅在内存中流转，服务器不记录、不缓存、不落盘）；互不干扰（房间层面的持续锁定与子频道层面的持续锁定独立运行）；即用即焚（子频道可以动态创建和销毁，关闭后密钥立即废弃）。

> **实践解读**："即用即焚"（密钥即时废弃）是子频道设计的核心机制——会话结束、密钥作废，连"解密历史"的余地都不留。这正是"数据最小化"原则在会话层的体现。

## Q9：频道跳转是怎么实现的？"下一个预密钥"是什么意思？

**A：** 在第四阶段，每个加密数据包除了承载消息外，还额外携带一个预密钥种子：当前包 = 加密消息 + "下一包的密钥种子"；下一包 = 使用上一包预告的种子派生新 EK，再携带下下一包的种子。

这就是持续锁定：攻击者即使截获了第 N 个包，也无法解密第 N+1 个包（密钥已变）；双方通过预密钥不断"跳频道"，形成前向安全链；虚拟房间确保这个跳转过程不被外部连接打断；子频道允许多个独立的前向安全链在同一房间内并行存在。

> **生活类比**：设想这样一个场景：持续锁定像"每次对话都换一个新暗号"——上一句话的最后一个字告诉你下一句的暗号。偷听者即使录下全部对话，没有"下一句暗号"的推导能力，也只能听到一片加密噪音。
> （以上为设想，非技术描述）

## Q10：为什么不做 32KB 的哈希交换？

**A：** 一种常见设计是在阶段二加入一个"碰撞机制"：双方生成 1024 个随机数，交换 32KB 的哈希值进行比对。这个设计在密码学上是冗余的——双方已经持有相同的 PSK，使用确定性派生函数，输出必然相同，交换哈希验证既不增加安全性，也不提供额外认证。

更重要的是，32KB 的交换带来流量关联（强指纹，可据此识别 ZT-DSP 握手）、DoS 放大（伪造握手请求迫使服务器转发巨量哈希数据）、延迟过高（200ms 延迟网络中接近性能极限）等问题。因此本协议不设冗余碰撞阶段，而是直接密钥派生（X25519 + HKDF）。

> **常见误区**："交换哈希验证"听起来更安全（多一次校验），实际是**冗余且有害**：双方派生的是同一个确定性函数结果，校验它等于"自己验证自己"；而 32KB 的流量特征反而给了攻击者识别协议的机会。安全设计不是"检查越多越好"，而是"每一步都有独立价值"。

## Q11：应急模式还在吗？

**A：已从本规范移除。** 原“应急哨声”（曾称“应急模式”）依赖当前工程与物理条件下不成立的前提，已从本规范删除，术语表中的对应条目同步移除。

## Q12：我可以修改协议的参数吗？

**A：可以，而且这是协议设计的核心特性。** ZT-DSP 是开放协议，所有参数均可自由修改：随机数长度（16 位、64 位、256 位、1024 位）、生成速率（每秒 1 个、128 个、1024 个、不设软件上限）、时间窗口（10 秒、30 秒、60 秒、自定义）、加密算法（AES-GCM、ChaCha20-Poly1305，或其他你信任的算法）。官方客户端还提供两个额外可调项：**时间戳窗口**（`--time-window`，默认 30 秒，per-peer 可配置，窄窗口高安全、宽窗口高可用）与**随机填充/时序抖动**（`--padding-min/max`、`--jitter`，默认关闭）。

但请注意：**客户端和服务器必须使用相同的参数才能通信。** 如果服务器声明"我只接受每秒 128 个 64 位随机数"，而你的客户端发送"每秒 1024 个 16 位随机数"，服务器会直接静默丢弃你的包，没有任何错误提示。这就是"库"的作用：服务器在其库中声明自己的参数方言，客户端必须拉取库并调参匹配。

> **实践提示（安全提醒）**：参数可以改，但**不建议削弱安全参数**：随机数长度低于 128 位、使用已知弱算法（如 MD5、SHA-1、DES）都会显著降低安全性。协议允许自由修改是为了"适配场景"（如低功耗设备用较短随机数），不是为了"图省事"。

## Q13：什么是"静默丢弃"？为什么不符合参数不返回错误？

**A：静默丢弃（Silent Drop）是 ZT-DSP 对抗架构的核心。** 如果服务器对每种错误都返回不同的错误码（如"长度错误"、"格式错误"），攻击者就可以通过错误码的差异来推断："这个端口在运行 ZT-DSP，而且它的参数是这样的……"

静默丢弃消除了这种信息泄露。无论攻击者发送什么，服务器都表现得像一个"关闭的端口"——没有任何响应。这使得大规模协议探测变得极其困难。

> **常见误区**：静默丢弃让你排查问题时"没有报错"，这不代表协议设计糟糕——它是**有意为之**的隐身机制。调试时请对照库文件逐项核对参数（长度/速率/窗口/算法），或在测试环境临时开启调试模式（生产环境务必关闭）。

## Q14：我可以用 ZT-DSP 做非法的事情吗？协议会不会协助我？

**A：ZT-DSP 是一个通信协议，就像 TCP/IP、HTTP、SMTP 一样，它是中性的技术工具。** 协议本身不鼓励、不阻止任何特定用途。它可以用于隐私保护的个人通信、记者与线人的安全联络、企业内部加密通信、学术研究和技术实验；也可以被滥用于非法内容的传播、犯罪活动的协调。

**协议无法区分合法与非法用途。使用者的行为责任由使用者承担，而非协议设计者或实现者。** 同时注意：技术匿名不等于法律匿名，密码学安全不等于操作安全（OPSEC）。在极端场景下，可靠的做法是不经由任何信道传输。

> **常见误区**：加密通信 ≠ 法律豁免。各国法律对加密通信、匿名网络有不同规定（部分国家要求"合法拦截"能力、禁止未经许可的加密）；"技术上不可破解"不代表"法律上不可追责"——你的设备、你接触的人、你的行为模式都可能成为执法依据。使用任何加密工具前，请了解并遵守当地法律。

# 附录 F：线上协议逐字节规范

> **【本附录导读】** 第四册讲"协议做什么"，本附录讲"线上到底长什么样"。本附录描述 ZT-DSP 的**全部四类线上帧**的精确字节布局、通用编码约定、上限常量与静默丢弃行为契约，每一句话都与官方实现（Python `zt_dsp_py` 与 Rust `zt_dsp_rs`）逐行核对。**任何两个自称兼容 ZT-DSP 的实现，必须在字节层面产出与本附录一致的网络流量**——否则阶段三确认标签校验会立刻失败。
>
> **【初学者关注点】** 本附录是"工程图纸"，零基础读者不必通读。建议先读 F.0 的四条通用约定建立直觉，再按需查阅各节。
>
> **【实现者关注点】** 本附录与附录 H（状态机/超时/错误矩阵）、附录 C（校验清单）配合使用。长度字段的**上限校验必须在读取载荷之前**完成——这是防内存炸弹的第一道闸。

## F.0 通用编码约定

```plain
大端序（Big-Endian / 网络字节序）
├── 含义：多字节整数的字节排列顺序——最高有效字节（最左边）先发送、先存储
├── 原理：数值 258（0x0102）按大端序在线上是字节 0x01 后跟 0x02；接收方按同一次序还原。网络协议传统上统一用大端序，故又称"网络字节序"
└── 出发方向：不同 CPU 架构的本地字节序不同（x86 是小端），线上必须固定一种，否则同一串字节会被解读成不同的数
```

以下约定适用于**全部四类帧**：

1. **传输载体**：TCP 字节流，没有消息边界。所有帧/包自带长度信息，接收方"读长度 → 读载荷"逐字段解析。
2. **字节序**：所有多字节整数一律**大端序（网络字节序）**。具体：4 字节长度字段与密文长度 = uint32 大端；8 字节序列号与时间戳 = uint64 大端；2 字节填充长度 = uint16 大端。
3. **长度前缀模式**：变长字段一律编码为 `[长度(4B uint32 BE)][载荷(长度字节)]`；定长字段（会话 ID、序列号、公钥、盐、时间戳、令牌哈希、next_seed）直接按字节排列，不带前缀。
4. **无魔数、无帧类型字段、无帧级 CRC**：帧的"类型"由它在握手流程中的位置（先后的序）决定，不在线上标注。帧级完整性由阶段三确认标签（握手期）与 GCM 认证（数据期）保证，CRC 仅存在于令牌层。
5. **先验长度、后读载荷**：接收方读出任何长度字段后必须先与上限比较（见 F.6），超限立即判定帧非法——绝不允许"按对端声明的长度分配内存"。
6. **原始帧参与认证**：阶段一双方帧的**原始字节**（含全部长度前缀）进入阶段三 transcript；对帧的任何"规范化重编码"（重排 JSON 键序、增删空白）都会导致确认标签不匹配。

## F.1 阶段一帧：身份宣告与参数交换

**帧布局（偏移表）：**

| 偏移 | 字段 | 长度 | 编码 | 说明 |
|------|------|------|------|------|
| 0 | param_len | 4B | uint32 BE | 参数 JSON 长度，≤ 4096 |
| 4 | param_json | param_len | UTF-8 JSON | 参数集（结构见下） |
| 4+P | identity_len | 4B | uint32 BE | 身份宣告长度，≤ 8192 |
| … | identity_blob | identity_len | 原始字节 | 默认 = 源令牌哈希(32B) ‖ 目标令牌哈希(32B)，共 64B；挂载 TCA 模块时由其替换为签名令牌等声明 |
| … | nonce_len | 4B | uint32 BE | 接入随机数长度，≤ 512 |
| … | nonce | nonce_len | 原始字节 | 接入随机数（派生公式见 4.2.1） |

**参数 JSON 的线上结构**：键按**字典序**排列、使用**紧凑分隔符**（`,` 与 `:`，无空格）、UTF-8 编码。参数 JSON **不含版本或协议标识字段**。官方默认参数下的实际线上字节（共 120 字节）：

```json
{"aead":"AES-256-GCM","hash":"SHA3-256","key_len":256,"module_flags":{},"random_len":256,"random_rate":1024,"window":60}
```

**参数校验规则**（双方各自构造与解析时都必须执行；任一规则不满足即判定参数非法）：

| 键 | 校验规则 | 官方默认值 |
|----|----------|-----------|
| random_len | 正整数，且为 **8 的倍数** | 256 |
| random_rate | 正整数 | 1024 |
| window | 正整数 | 60 |
| key_len | 仅允许 **128 / 192 / 256** | 256 |
| hash | 官方支持 SHA3-256/384/512 与 SHA-256/384/512 | `"SHA3-256"` |
| aead | 官方实现仅含 AES-256-GCM | `"AES-256-GCM"` |
| module_flags | 键必须为字符串；值仅允许字符串/整数/浮点/布尔/列表/字典/null；**嵌套深度 ≤ 32，节点总数 ≤ 1024** | `{}` |

**参数匹配核对**：双方必须对以下 7 项**逐项相等**，核对按此固定顺序进行（任一项不等即停止）：
`random_len → key_len → window → random_rate → hash → aead → module_flags`。

**接入随机数（nonce）的线上契约（精确化）**：

- 派生：`nonce = HKDF-SHA3-256(IKM = PSK, salt = 本地新鲜随机盐(32B), info = "ZT-DSP-PHASE1-NONCE-v3", 输出长度 = random_len / 8 字节)`
- **派生所用的盐不随帧传输**（每次握手本地新生成）。因此**核心协议的对端校验只有一条：`len(nonce) × 8 == 对端声明的 random_len`**——对端无法（也不试图）重算该随机数，"它是否由正确 PSK 派生"的验证由确认标签间接承担（PSK 错 → MK 错 → 标签必错）。统计层面的校验（随机数质量增强等）属于扩展层职责。
- 双方各发各的 nonce，两个 nonce 相互独立。

**交换顺序**：发起方先发完整帧 → 响应方读全帧、验参、校验 nonce 长度（以及扩展层验证，若有）→ **全部通过后**响应方才回发自己的帧。默认参数（JSON 120B + 身份宣告 64B + nonce 32B）下，阶段一帧 = 4+120+4+64+4+32 = **228 字节**。

## F.2 严格静默丢弃行为规范（Responder 侧行为契约）

4.3 节讲了静默丢弃的**思想**，本节给出它的**行为契约**——"严格静默"五个要素，缺一不可：

1. **不发送任何字节**。包括错误响应、空包、TCP 层以外的任何应用层回应。
2. **不主动关闭连接**。关闭连接（FIN/RST）本身就是一个可观测信号——攻击者可据此区分"参数不匹配被拒"与"端口根本没人听"。
3. **挂起读取并丢弃后续数据**：以 8192 字节为块持续 `recv` 并丢弃，直到对端关闭或挂起时长耗尽。挂起时长默认 = 握手超时（**15 秒，可配置**；服务器嵌入场景建议调小并配合 per-IP 限流，防止恶意连接长期占用连接槽）。
4. **诊断只进本地 stderr**：丢弃原因（如"阶段一解析失败""参数不匹配: random_len"）打印给本机运营者看，**绝不进入网络侧**，也不应接入对外日志系统。
5. **网络观感与"关闭端口"不可区分**：从攻击者视角，对一个不存在服务的扫描和一个参数错误的 ZT-DSP 服务器，看到的应该是同一种"无声"。

**触发点全表**（响应方视角；任一触发即进入严格静默）：

| 阶段 | 触发条件 |
|------|----------|
| 阶段一 | 帧解析失败（长度超限 / JSON 无效 / UTF-8 错误 / 超时）；参数非法（校验规则不满足）；7 项参数不匹配（任一项）；nonce 长度 ≠ 声明的 random_len；TCA 令牌验证失败 / CRL 命中 / 服务器库声明不符（挂载扩展时） |
| 阶段二 | 帧读取失败或超时；公钥长度 ≠ 32B；DH 计算失败（**低阶点公钥**如全零、u=1，或 **DH 输出全零**） |
| 阶段三 | 确认帧读取失败、长度 ≠ 32B 或超时 |

**发起方的不对称性**：发起方在阶段一已主动发出帧，对端本来就知道它存在，因此发起方检测到失败时**主动断开并抛出本地异常**（如 ZTDSPParamError）不破坏静默性。静默约束只针对"被动等待的一方"。

**时序一致性**：静默路径应避免与正常路径产生可测的响应时间差异（静默路径本来就无响应，此处指"挂起时长"不要因错误类型而变化）。

## F.3 阶段二帧：临时公钥与会话盐交换

**发起方 → 响应方（共 68 字节）：**

| 偏移 | 字段 | 长度 | 编码 | 说明 |
|------|------|------|------|------|
| 0 | pub_len | 4B | uint32 BE | 恒为 32 |
| 4 | pk_A | 32B | 原始字节 | 发起方 X25519 临时公钥（Raw 编码） |
| 36 | session_salt | 32B | 原始字节 | 发起方生成的会话盐，**明文**传输，随后作为 HKDF 的 salt 参数 |

**响应方 → 发起方（共 36 字节）：**

| 偏移 | 字段 | 长度 | 编码 | 说明 |
|------|------|------|------|------|
| 0 | pub_len | 4B | uint32 BE | 恒为 32 |
| 4 | pk_B | 32B | 原始字节 | 响应方 X25519 临时公钥 |

**顺序约束（安全关键）**：响应方必须**先收全发起方帧、完成 DH 计算，全部通过后才发送响应帧**。若先回应后算 DH，低阶点/无效公钥的攻击者就能在"收到响应帧"与"连接被断"之间制造一个可观测的时序差——"验证失败前已泄露响应帧"。这正是 4.2.2 所述"严格静默扩展至阶段二"的工程含义。

**DH 失败判定**（两条件任一即静默丢弃）：对端公钥长度 ≠ 32 字节；X25519 计算输出为**全零**（低阶点攻击的数学特征——恶意公钥使共享秘密坍缩为常量）。

## F.4 阶段三帧：确认标签交换

**帧布局（双方相同，各发一次）：**

| 偏移 | 字段 | 长度 | 编码 | 说明 |
|------|------|------|------|------|
| 0 | confirm_len | 4B | uint32 BE | 恒为 32 |
| 4 | tag | 32B | 原始字节 | HMAC-SHA3-256 确认标签 |

**transcript 的精确构造**（双方按同一公式独立拼接，顺序固定）：

```plain
transcript = 阶段一发起方原始帧（含全部长度前缀，逐字节）
           ‖ 阶段一响应方原始帧（含全部长度前缀，逐字节）
           ‖ session_salt（32 字节）
           ‖ 发起方临时公钥（32 字节）
           ‖ 响应方临时公钥（32 字节）

tag_init = HMAC-SHA3-256(MK, "ZT-DSP-CONFIRM-INIT-v3" ‖ transcript)
tag_resp = HMAC-SHA3-256(MK, "ZT-DSP-CONFIRM-RESP-v3" ‖ transcript)
```

> **transcript 不含版本或协议标识**：拼接材料里没有任何版本串。对端是否遵循同一份文档，由 `tag_init` / `tag_resp` 校验体现——不一致即标签不匹配。

**交换时序（按官方实现）**：

1. 发起方发送 `tag_init` 帧
2. 响应方读取该帧——**只有帧级错误**（读取失败 / 长度 ≠ 32 / 超时）触发严格静默
3. 响应方发送 `tag_resp` 帧（注意：此时**尚未**校验对方标签内容）
4. 双方各自以**恒定时间比较**核对对方标签；任一方不匹配 → 擦除全部密钥材料 → 握手失败（发起方与响应方均报 ZTDSPSecurityError）

> **常见误区**："响应方验证通过后才发自己的标签"是一种常见误解，与官方实现不符。响应方是"先发后比"。这不构成安全漏洞：标签是双向各自的 HMAC，攻击者无法靠"抢先发一个正确标签"冒充任何一方——它没有 MK，算不出任何一方的正确标签；比较错的一方会立即擦除密钥并终止。

**绑定意义**：transcript 覆盖了双方阶段一帧的**原始字节**——参数 JSON、身份宣告、接入随机数全部在内。任何中间人对身份宣告或参数的替换、任何一方实现上的"规范化重编码"，都会导致 transcript 不一致、标签必错。TCA 扩展层对参数/身份的合法修改也因"改的是双方都能看到的原始帧"而不会误伤（双方绑定的是同一段字节）。

## F.5 阶段四数据包：加密数据传输

**明文头（44 字节，固定）：**

| 偏移 | 字段 | 长度 | 编码 | 说明 |
|------|------|------|------|------|
| 0 | session_id | 32B | 原始字节 | 会话路由标识（派生见 4.2.3），服务器据此投递 |
| 32 | seq | 8B | uint64 BE | 发送方序列号，首个数据包为 0 |
| 40 | ct_len | 4B | uint32 BE | 密文长度，≤ 1 MiB |

**密文** = `AES-256-GCM(EK_方向, nonce, payload, AAD)`，尾部自带 16 字节认证标签。

**payload（GCM 明文，即加密前的内部载荷）偏移表：**

| 偏移 | 字段 | 长度 | 编码 | 说明 |
|------|------|------|------|------|
| [0:8] | 时间戳 | 8B | uint64 BE | 毫秒级 Unix 时间戳 |
| [8] | fmt | 1B | uint8 | `0x00` = 无随机填充；`0x01` = 带随机填充 |
| [9:41] | dst_token_hash | 32B | 原始字节 | 目标令牌哈希（本包"收件人"） |
| [41:73] | src_token_hash | 32B | 原始字节 | 源令牌哈希（本包"发件人"） |
| [73:…] | 用户明文 | 可变 | 原始字节 | 实际消息内容；心跳包此处为空 |
| （fmt=0x01） | 随机填充 | pad_len | 原始字节 | 真随机填充，见附录 G.2 |
| （fmt=0x01） | pad_len | 2B | uint16 BE | **紧贴 next_seed 之前**（即位于载荷倒数第 34~33 字节），接收方据此从尾部定位填充 |
| [-32:] | next_seed | 32B | 原始字节 | 下一包的棘轮种子 |

- **最小载荷长度** = 8 + 1 + 32 + 32 + 32 = **105 字节**（fmt=0x00 且用户明文为空，即心跳包的载荷）
- **用户明文上限** = 1 MiB − 64 − 1 − 64 − 8 − 32 − 2 − 2048 = **1046357 字节**（为帧头、认证标签、填充上限预留余量）
- **默认参数下的心跳包**（无填充）线上总长 = 44（头）+ 105（载荷）+ 16（GCM 标签）= **165 字节**——互操作测试可用它做尺寸断言

**nonce（12 字节）**：`0x00000000（4B）‖ seq（8B uint64 BE）`。序列号单调递增保证同一密钥下 nonce 绝不重用。

**AAD**：`session_id ‖ seq（8B uint64 BE）`，共 **40 字节**（session_id 32B + seq 8B）。路由字段"可见但防篡改"。**AAD 不含任何版本或协议标识**。

**接收校验流水线（顺序固定，任一步失败立即终止处理）**：

| 步骤 | 校验 | 失败含义 | 失败后果 |
|------|------|----------|----------|
| 1 | `seq > seq_recv`（seq_recv 初始为 −1） | 重放或乱序旧包 | 会话终止（安全错误） |
| 2 | `session_id == 本地会话 ID` | 串频或旧会话残留包 | 会话终止（安全错误） |
| 3 | GCM 解密与认证（AAD 参与认证） | 篡改或密钥不匹配 | 会话终止（安全错误） |
| 4 | 载荷长度 ≥ 105B | 结构残缺 | 会话终止（协议错误） |
| 5 | `fmt ∈ {0x00, 0x01}` | 未知载荷格式 | 会话终止（安全错误） |
| 6 | 结构长度自洽：固定头 + 尾部（含 pad_len ≤ 2048）不超过载荷总长 | 越界/负切片攻击 | 会话终止（协议错误） |
| 7 | 令牌哈希双向校验：包内 dst == 本地身份，src == 对端身份 | 流量返送 / 串频 / 身份伪造 | 会话终止（安全错误） |
| 8 | 时间戳窗口：`|now − ts| ≤ time_window` | 已认证但超窗的重放/延迟包 | **特殊**：不终止会话——仍旋转 EK、推进 seq_recv，仅丢弃明文（防棘轮失步，见 4.2.4 接收流程第 5 步） |

**发送侧状态前滚（"先消耗状态，后尝试发送"）**：加密发送**之前**依次完成——生成 next_seed → `new_EK = HKDF-SHA3-256(EK ‖ next_seed, info = "ZT-DSP-EK-ROTATE")` → 擦除旧 EK、换入 new_EK → `seq += 1`。因此发送失败时密钥也已前滚，会话不可恢复（只能重连），但攻击者永远无法利用"发送失败导致状态未前滚"来重放。

# 附录 G：流量分析防御实施细节

> **【本附录导读】** 5.4 节的防御矩阵给出了"用什么防"，本附录给出"精确怎么编码"。填充、抖动、时间戳窗口三项防御全部是**协议行为层**的规定，两个实现即使算法正确、参数不同，也能互通——这正是它们"可单边启用"的设计价值。
>
> **【实现者关注点】** 填充的剥离依赖 fmt 标记与 pad_len 字段的精确定位（G.2），编码错误会直接导致对端解析失败；抖动是纯本地行为（G.3），不影响线上字节。

## G.1 三种流量指纹与对应防御

| 指纹类型 | 泄露什么 | 对应防御 | 启用方式 |
|----------|----------|----------|----------|
| 长度指纹 | 消息大小 → 内容类型猜测、行为画像 | 随机填充（G.2） | 发送方单边 |
| 时序指纹 | 发送节奏 → 打字习惯、自动化特征 | 时序抖动（G.3）+ 心跳基线（G.5） | 发送方单边 |
| 新旧混淆缺失 | 延迟投递的旧包被当作新包处理 | 时间戳窗口（G.4） | 双方各自配置 |

## G.2 随机填充的精确编码

- **配置**：发送方持有一对 `(padding_min, padding_max)`，满足 `0 ≤ min ≤ max ≤ 2048`（单位：字节）。官方 CLI 参数 `--padding-min` / `--padding-max`（须同时给出）；**默认不配置 = 关闭填充**。
- **每包独立**：`pad_len = randbelow(max − min + 1) + min`（区间内均匀分布），填充内容为**真随机字节**（不可用零填充——零串是低熵指纹）。
- **线上编码**：启用时 `fmt = 0x01`，载荷布局变为 `…用户明文 ‖ 随机填充(pad_len B) ‖ pad_len(2B uint16 BE) ‖ next_seed(32B)`。**pad_len 字段必须紧贴 next_seed 之前**——接收方从载荷尾部固定位置（倒数第 34~33 字节）读它，从而不需要知道明文长度就能定位填充边界。
- **接收剥离**：接收方看到 `fmt = 0x01` 才解析填充；`fmt = 0x00` 的包即使来自"会填充的对端"也合法（**填充是逐包决定的，单边启用、无需协商**）。pad_len > 2048 → 协议错误。
- **成本**：每包多传 pad_len 字节 + 2 字节；带宽换隐私。参考建议区间 512~2048 字节，足以抹平常见消息的长度分层。

## G.3 发送时序抖动

- **配置**：`jitter ≥ 0`（秒），官方 CLI `--jitter`，默认 0（关闭）。
- **行为**：每个数据包在加密完成、真正写入 socket 之前，随机等待 `[0, jitter)` 区间的时长。
- **语义**：纯**本地发送行为**，不改变任何线上字节；对端无感知、无需配合。
- **设计边界**：抖动只平滑"发送时刻"，不平滑"发包速率分布"——需要对抗统计节奏分析时，应与心跳基线（G.5）组合使用。

## G.4 时间戳窗口

- **配置**：`time_window > 0`（秒），官方 CLI `--time-window`，默认 30；**per-peer 可配置**（同一客户端对不同对端可用不同窗口）。
- **语义**：接收方校验 `|当前时间 − 包内时间戳| ≤ time_window × 1000`（毫秒比较）。窗口内正常交付；**超窗但已通过 GCM 认证的包，仍执行棘轮旋转与序列号推进，只丢弃明文**（见 F.5 流水线第 8 步）——这条"可用性补全"是防"发送方已旋转、接收方未旋转"的永久失步的关键，**实现者不得省略**。
- **权衡**：窄窗口（如 10s）→ 更快拒绝延迟投递的重放包，但要求双方时钟偏差小、网络延迟低；宽窗口（如 60s）→ 容忍慢网络与时钟漂移，代价是重放包的"有效期"更长。重放的核心防线始终是序列号（F.5 第 1 步），时间戳窗口是第二道。

## G.5 心跳即基线流量

- 官方客户端每 **30 秒**发送一个**空明文**心跳包（默认参数下线上 165 字节，见 F.5）。
- 三重作用：① 检测半开连接（TCP 对"对端已消失"通常无感知，直到 send 失败）；② 压平"沉默期"——流量观察者无法从"长时间无包"推断会话空闲；③ 参与棘轮旋转，使密钥链即使无消息也在持续前进。
- 心跳失败（发送错误）即视为连接已断，会话清理。

## G.6 部署组合建议

| 部署场景 | 填充 | 抖动 | 时间戳窗口 | 说明 |
|----------|------|------|------------|------|
| 普通隐私通信 | 关闭 | 0 | 30s（默认） | 开销最小，机密性不受影响 |
| 进阶（反长度画像） | 512~2048B | 0~0.5s | 30s | 消息长度被抹平 |
| 高对抗 | 1024~2048B | ≥ 1s | 15~30s | 配合发送时序抖动（G.3） |
| 高延迟/不可靠链路 | 可选 | — | 60s+ | 宽窗口换可用性，重放防护交给序列号 |

        │ 构建完成                            │ nonce 长度不符）

┌──────────────┐  发送阶段一帧(228B+)   [断开 + 擦除密钥]

        │ 收到对端帧            │ 对端关闭   │

        │ 收到

## H.2 响应方（Responder）状态机

```plain
[新建 Peer] ──→ [LISTENING]（accept 进入连接）
                        │ 收到阶段一帧
                        ▼
                ┌────────────────┐  解析帧 → 参数校验 → 7 项比对
                │ PHASE1_VALIDATE│  → nonce 长度 → （扩展层验证）
                └────────────────┘
                        │              │ 任一失败
                        │通过          ▼
                        │      ┌────────────────┐
                        │      │ SILENT_HOLD    │ 不发送、不关闭；
                        │      │ （15s，可配置） │ 挂起吞字节直至对端
                        │      └───────┬────────┘ 关闭或挂起超时
                        │              ▼
                        │        [CLOSED]（全程零响应）
                        ▼
                ┌────────────────┐  本帧已构建（不发送）
                │ PHASE1_REPLIED │
                └────────────────┘
                        │ 接收 [pub_len‖pk_A‖salt]
                        ▼
                ┌────────────────┐  先收全帧 → 先算 DH
                │ PHASE2_PRECHECK│──帧错误/低阶点──→ SILENT_HOLD
                └────────────────┘   （发送任何字节之前！）
                        │ DH 成功 → MK 派生
                        ▼
                ┌────────────────┐  回送 [pub_len‖pk_B]（36B）
                │ PHASE2_REPLIED │
                └────────────────┘
                        │ 接收确认帧
                        ▼
                ┌────────────────┐
                │ CONFIRM_RECV   │──帧级错误──→ SILENT_HOLD
                └────────────────┘
                        │ 收到 → 发送自己的 tag_resp
                        ▼
                ┌────────────────┐  恒定时间比较 tag_init
                │ CONFIRM_CHECK  │────不匹配──→ [擦除全部密钥 + 关闭]
                └────────────────┘
                        │ 匹配 → 擦除 MK/锚点/PSK
                        ▼
                  [ESTABLISHED]（同发起方；数据阶段行为一致）
```

> **两台状态机的三个不对称点**：① 阶段一发起方先发、响应方验完才回；② 阶段二响应方"先算 DH 再回应"（低阶点静默的前提）；③ 静默丢弃只约束响应方——发起方失败时主动断开（F.2）。

## H.3 全量计时器表

| 计时器 | 默认值 | 起点 | 终点 | 超时行为 |
|--------|--------|------|------|----------|
| 握手超时 | 15s | 进入每个握手阶段 | 该阶段完成 | 阶段失败：响应方静默挂起；发起方断开并报超时 |
| 读取总时限（Slowloris 防护） | 15s（= 握手超时） | 阶段内读第一个字节 | 整帧读毕 | **整帧共享一个截止时间**，而非"每次 recv 重新计时"——攻击者无法用"每 14 秒发 1 字节"无限拖延 |
| 半包超时 | 同上 | 已读部分字节后截止时间耗尽 | — | **强制关闭 socket**：帧同步已破坏，无法恢复；区别于"起始超时"（一个字节都没读到，允许上层安全重试） |
| 数据阶段超时 | 60s | 握手完成后 | 会话结束 | 报超时并清理会话（心跳 30s 能赶上 60s 窗口） |
| 心跳间隔 | 30s | 上一次心跳（或会话建立） | 下一次心跳 | 发送失败 → 判定半开连接，清理会话 |
| 静默挂起时长 | 15s（= 握手超时，可配置） | 进入静默丢弃 | 对端关闭或时长耗尽 | 关闭连接（此时已"无声"了 15s） |
| 等候池超时（服务器侧） | 30s | 进入等候池 | 配对成功或超时 | 登记表清除，防内存占用 |
| 时间戳窗口 | 30s（per-peer 可配置） | — | — | 不是计时器而是校验阈值；超窗包处理见 F.5 第 8 步 |

> **常见误区**：Slowloris 防护的关键不是"15 秒这个数"，而是**截止时间的共享方式**。若每个 `recv` 都独立享受 15 秒超时，攻击者拖一次帧就能把 4 字节长度字段读成 60 秒；共享截止时间后，无论对方怎么挤牙膏，整帧预算只有 15 秒。

## H.4 错误处理矩阵（阶段 × 失败 → 双方行为）

| 阶段 | 失败方式 | 发起方行为 | 响应方行为 |
|------|----------|------------|------------|
| 阶段一 | 构建帧失败（参数非法/nonce 长度与声明不符） | 本地异常，不发送 | 本地异常，不监听侧影响 |
| 阶段一 | 对端帧解析失败 / 参数非法 / 7 项不匹配 / nonce 长度不符 / TCA·CRL·库声明失败 | 等待对端回帧 → 15s 超时后断开 | **严格静默**（挂起 15s 吞字节，零响应） |
| 阶段二 | 对端公钥长度 ≠ 32B / 读取失败 / 超时 | 断开 + 擦除 + 协议/超时错误 | **严格静默** |
| 阶段二 | DH 失败（低阶点、全零输出） | 断开 + 擦除 + 密码学错误（发起方已发帧） | **严格静默**（DH 前置到发送之前） |
| 阶段三 | 对端确认帧错误 / 超时 | 断开 + 擦除 + 超时错误 | **严格静默** |
| 阶段三 | 标签内容不匹配 | 恒定时间比较失败 → **擦除全部密钥** + 安全错误，断开 | 同左（双方独立比较，各自失败） |
| 数据期 | seq 重复/回退（重放） | —（由发送方触发的对端侧错误） | 恒定时间路径前已拦截 → **会话终止 + 擦除**，安全错误 |
| 数据期 | session_id 不匹配 / GCM 认证失败 / fmt 未知 / 结构矛盾 / 令牌哈希双向校验失败 | 同上（这些校验都发生在接收方） | **会话终止 + 擦除**（安全或协议错误） |
| 数据期 | 时间戳超窗（但 GCM 已通过） | — | **不终止**：旋转 EK、推进 seq_recv、丢弃明文（返回空明文） |
| 数据期 | 发送失败（断连/BrokenPipe/OSError） | **会话不可逆失步**：密钥已前滚无法回收 → 清理会话，提示重连 | 对端将因读取失败/超时终止 |
| 数据期 | 60s 无任何包（半开连接） | 心跳发送失败即触发清理（"连接可能已断开"） | 同左 |
| 任意 | 握手任一步抛出异常 | 握手入口统一清理：**擦除 PSK/MK/锚点/EK 全部材料** | 同左 |

## H.5 协议层异常体系

实现者应把本地错误收敛为**类型化异常**，便于上层区分"该重试"与"该终止"（以下为官方客户端的异常树，其他实现建议保留同样的分类粒度）：

```plain
ZTDSPError（协议异常基类）
├── ZTDSPSecurityError
│   └── 含义：安全事件——PSK 不匹配、锚点确认失败、重放/乱序、会话 ID 不匹配、
│       AEAD 解密失败、未知载荷格式、令牌哈希双向校验失败
│   └── 处置：一律终止会话并擦除密钥；不可重试、不可忽略
├── ZTDSPParamError
│   ├── 含义：参数问题——双方参数不匹配、参数值非法
│   └── 处置：握手期失败；发起方断开重试前先核对参数
│   └── SilentDropError（其子类）
│       └── 含义：**本端已进入严格静默**（F.2）——这是一个"信号"而非普通错误：
│           上层捕获后绝不得再向对端发送任何数据或关闭连接（静默路径已接管）
├── ZTDSPProtocolError
│   └── 含义：帧格式问题——长度超限、JSON 无效、结构长度矛盾、nonce 长度不符
│   └── 处置：握手期按角色走静默/断开；数据期终止会话
├── ZTDSPCryptoError
│   └── 含义：密码学失败——弱 DH 输出（低阶点）、派生失败、算法不支持
│   └── 处置：同安全事件（低阶点就是攻击）
└── ZTDSPTimeoutError
    └── 含义：超时——握手超时、读取总时限耗尽、半包超时、数据阶段无包
    └── 处置：半包超时必伴随 socket 强制关闭；其余按 H.4 矩阵
```

## H.6 失败后的密钥清理语义

- **握手期任何失败**（含钩子中止、异常逃逸）→ 入口统一执行完整清理：PSK、MK、锚点、EK_send/EK_recv 全部安全清零，会话状态复位。**绝不带密钥退出**——这是"最小暴露面"的硬要求（4.2.3 步骤 6 的失败路径版本）。
- **数据期发送失败** → 密钥已前滚（F.5），会话**不可逆失步**：清理并要求重连。peer 对象是一次性的——重连必须新建 Peer 并重新提供 PSK（握手成功后 PSK 已按协议擦除，旧对象无法复用）。
- **数据期接收侧安全错误** → 会话终止 + 完整清理；安全事件可选择上报给上层审计（但注意第五册的无日志原则——本地审计与对外记录是两回事）。
- **清理必须幂等**：发送、接收、心跳三条线程都可能最先发现会话死亡，清理逻辑必须保证"socket 恰好关闭一次、密钥恰好擦除一次、收尾通知恰好触发一次"，否则长期运行的服务器会积累半开 socket（文件描述符泄漏）与密钥残留。
