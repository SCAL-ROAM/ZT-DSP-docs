## 11. 版本与兼容

- 协议版本当前**未在协议内协商**（§5.3 缺口）。跨实现一致性靠部署侧配置保证。
- 派生材料与帧格式与现有 1.0.0 实现一致，因此本规范的参数与现行实现**可互通**。

## 12. 已知局限与演进方向

| 局限 | 影响 | 演进方向 |
|---|---|---|
| **无显式版本面** | 无法强制版本一致，无 fail-closed 的降级阻断 | 参数集增加必填版本字段；缺失即判非法；版本随阶段一帧进 transcript |
| **`key_len` 无下限** | 明文参数可被改写为更弱密钥 | 设 256 位下限，对对端提议同样强制 |
| **无后妥协自愈**（纯对称链） | 密钥泄露后该会话全程可读 | 数据面引入周期性 DH 重协商，形成双棘轮 |
| `ek` 兼任消息密钥与推进输入 | 单点泄露连锁到全链 | 拆分 root / chain / message 三层 |
| 无第三方可验证凭据 | 无法接入「出示凭据」类体系 | 剖面级令牌格式（核心明确不提供） |
| KEM 为 X25519 | 抗量子不足 | 双 KEM 组合过渡，需与版本面同步引入 |
| 零丢包容忍 | 不适合不可靠传输 | 剖面覆盖 + 会话恢复机制 |
| 无吊销 | PSK 泄露后无法作废 | 属部署/CA 体系，不属核心 |

> 上表第一、二行是**已知缺陷**，尚未修复。第三行起是**结构性局限**。
在第一、二行被修复之前，对外陈述不得使用「不可静默降级」「版本可强制协商」这类说法。

## 10. 使用剖面

### 10.1 通讯剖面

**适用范围**：两方在**可能不可信的中间网络**上交换消息，且要求服务端看不到内容、无法关联会话，旁观者无法确认两端是否在通讯，身份通过令牌而非连接来源证明。

**对核心的使用**：全部四个阶段。

**附加要求（不属于核心）**：

| 要求 | 内容 | 为什么不在核心里 |
|---|---|---|
| 服务端静默丢弃 | 服务端无法路由时，**必须表现得像正常转发一样丢弃** | 只在有服务端转发时才有意义 |
| 随机填充 | 数据帧载荷长度随机化，避免泄漏消息大小 | 元数据防护，与应用语义绑定 |
| 服务端不可关联 | 会话标识与身份解绑，且不得在同一会话内复用 | 需要身份令牌体系配合 |
| 房间号派生出 PSK | 房间号经 KDF 派生，房间号原文不上线 | 属身份目录的设计 |
| 身份令牌（TCA） | 由权威方签发、含绑定字段、带期限 | 依赖外部信任体系 |

**追加的威胁条目**：服务端枚举房间、服务端关联会话、旁观者确认通讯发生——各对应「房间号空间足够大」「会话标识与身份解绑」「帧长度随机化且无协议级错误信号」。

**不适用**：需要离线阅读历史消息、需要可靠送达或重放语义、需要跨会话搜索或集中审计。

### 10.2 鉴权剖面

**为什么是独立剖面**：协议本就以 PSK 为信任根，**知道同一个 PSK 即同一身份**。因此鉴权不需要新协议，只需要**把核心跑完前三个阶段**：

```
阶段一  身份声明（可选） + 参数协商
阶段二  密钥协商
阶段三  确认          <-- 到这里，认证已经完成
阶段四  加密帧流      <-- 通讯用途才需要；鉴权用途可不用
```

**适用范围**：设备接入服务、点对点配对、人员登录服务——任何「双方各持一把相同钥匙」的准入场景。

**对核心的使用**：阶段一至三必需，四可选；**可短连接**，无需长连接；顺序语义不适用。

**剖面职责（核心不管的）**：

| 事项 | 为什么归剖面 |
|---|---|
| PSK 的分发 | 核心只假定双方已通过带外方式共享 PSK |
| PSK 的存储 | 属宿主安全：安全元件、文件权限、口令管理器 |
| PSK 的轮换与吊销 | 需要生命周期管理，不属协议 |
| 失败计数与锁定 | 核心不防 DoS，限速必须由服务端实施 |
| 向第三方出示凭据 | 核心明确不提供；若需要，属独立设计 |

**追加的威胁条目**：暴力枚举 PSK（要求熵充足 + **服务端限速**）、重放旧的认证交互（每次全新临时密钥与盐）、参数改写（确认标签覆盖 transcript）、弱密钥接入（**当前 `key_len` 无下限，是已知缺口**）。

**明确不做**：不产出第三方可验证令牌；不提供用户级身份（认证的是「持有 PSK 的那一端」）；不提供吊销查询；不提供后妥协自愈。

**失败处理**：失败必须显式，**不得静默降级为单向认证**；失败后**不得自动重试**同一 PSK（避免被当作在线猜测预言机）。

### 10.3 剖面组合

两个剖面可串联：先跑鉴权剖面拿到会话材料，再用同一材料建立通讯剖面的帧流。

> 此时**后妥协自愈仍然不存在**（§2.2）：会话材料泄露后，该会话后续流量均可读。

### 10.4 新增剖面的准入

1. **用途**——它解决什么问题，核心加什么也不够？
2. **追加了什么**——要求 / 语义 / 威胁条目，各是哪几条？
3. **是否覆盖核心假设**——若是，必须逐条标注被覆盖的条款与理由。
4. **是否只是换应用**——如果差异只在「载荷长什么样」，那是**应用**，不是剖面。

> 第 4 条最容易被滥用：**换载荷不构成剖面**。

## 7. 帧与通道

### 7.1 帧头（定长）

| 字段 | 长度 | 说明 |
|---|---|---|
| `session_id` | 16 B | 会话标识（明文） |
| `seq` | 8 B | 单调序号（明文，同时作为 AEAD nonce 基础） |
| `ct_len` | 4 B | 密文载荷长度（明文） |

### 7.2 载荷

全部载荷（含时间戳、身份声明、`next_seed`）都在 AEAD 内，**明文头只有会话标识、序号与长度**。

### 7.3 顺序与重放

- 接收方要求 `seq` **严格递增**；`seq <= 已收最大值` → **立即终止会话**。
- 时间戳超出落地窗但认证通过 → **仅丢弃该帧明文，不终止会话**。
- 认证失败（AEAD 不匹配）→ 终止。

> 严格递增意味着**零丢包容忍**：任何乱序或重复都结束会话。这是刻意的 fail-closed 选择；需要不可靠传输的剖面必须覆盖该规则。

## 8. 认证结论

### 8.1 成功判据

阶段三完成且以下三条**同时**成立：

1. 双向确认标签均校验通过（双方持有同一 PSK 且 transcript 一致）；
2. 参数集逐项一致；
3. 对端身份声明（若使用）通过验证。

任何一项失败 → 终止并清除密钥。

### 8.2 可用于鉴权的输出

| 输出 | 用途 |
|---|---|
| 会话密钥材料 | 直接用于本次会话的加密通信 |
| 会话标识 | 本次会话的句柄，**不可跨会话关联到身份**（除非剖面要求） |
| 认证结论 | 「对端持有同一 PSK」这一布尔事实 |

> 本规范**不产出可供第三方验证的凭据**。若调用方需要「向某个服务证明自己走过本认证」，那是**剖面或应用层**的职责。

## 9. 剖面机制

### 9.1 剖面能做什么

剖面**只能追加**，不能削减核心：追加**要求**、追加**语义**、追加**威胁模型条目**；在明确标注的前提下**覆盖**核心的传输假设。

### 9.2 剖面不能做什么

- 削弱核心的认证强度、跳过阶段、允许降级。
- 复用或延长已销毁的密钥材料。
- 把核心的「不提供」清单（§2.2）变成「已提供」。

### 9.3 剖面标识

实现必须显式声明所运行的剖面，**跨剖面互操作不被假定**。

## 5. 密码学套件与参数协商

### 5.1 固定套件

| 项 | 取值 |
|---|---|
| KEM | X25519（唯一允许值） |
| AEAD | AES-256-GCM（唯一允许值） |
| 哈希 | SHA3-256 / SHA3-512 / SHA2-256 / SHA2-512（白名单，禁用 MD5/SHA-1） |
| KDF | HKDF-SHA3 |
| 签名 | Ed25519（仅用于身份声明，不参与密钥派生） |

### 5.2 参数集（**现状**）

阶段一的参数集是 JSON，键按字典序、紧凑分隔符。字段：

| 参数 | 含义 |
|---|---|
| `key_len` | 会话密钥长度 |
| `window` | 落地时间窗 |
| `random_len` / `random_rate` | 随机数注入策略 |
| `hash` / `aead` | 套件选择 |
| `module_flags` | 可选模块开关 |

**参数集不含版本字段**：默认参数下 JSON 固定 120 字节，阶段一帧 228 字节（见总指导附录 B / F.1）。

### 5.3 降级防护的现状与缺口

**已有**：参数集整体进入 transcript，被阶段三确认标签覆盖 → 改写任一参数都会导致确认失败。

**缺口（必须承认）**：

1. **没有显式版本面**：双方无从判断对方是否遵循同一份文档；「版本相同」只能靠约定，不能靠协议强制。
2. **`key_len` 无下限**：明文协商的参数可被改写为更弱的密钥长度。
3. **无 fail-closed 的拒绝路径**：不存在「对端未声明版本 → 直接拒绝」的规则，因为根本没有版本字段。

> 这三条是已知的、**当前确实存在**的缺陷，改进方向见 §12。
在它们被修复前，本规范不得声称具备「不可静默降级」性质。

## 6. 密钥派生

### 6.1 材料

```
mk        = HKDF(PSK || DH, INFO_MK, salt)        // 会话主密钥
anchor    = HMAC(mk, INFO_ANCHOR)                // 双向确认材料
ek        = HKDF(mk || anchor || role, INFO_EK)  // 方向相关初始密钥
session_id = HKDF(anchor, INFO_SID)              // 会话标识（明文可见）
```

`DH = X25519(本方临时私钥, 对端临时公钥)`。

### 6.2 逐帧密钥推进

```
msg_key = ek
ek_next = HKDF(ek || next_seed, INFO_EK_ROTATE)
```

每个帧携带自己的 `next_seed`，密钥随帧推进并逐帧销毁。

### 6.3 必须承认的局限

- **纯对称链，无 DH 参与 → 无后妥协自愈**。
- `ek` 同时充当 AEAD 密钥与下一次推进的输入。成熟设计通常拆分 root / chain / message 三层，**消息密钥绝不回流**。本规范维持现状以保持与现有实现一致，改进见 §12。

## 2. 目标与非目标

### 2.1 目标（按优先级）

1. **双方相互认证**：基于 PSK，双方互相证明持有密钥，抵抗中间人与冒充。
2. **密钥协商**：产生第三方不可预测的会话密钥。
3. **前向保密**：会话密钥泄露后，已建立的会话流量不可回溯解密。
4. **防重放与防乱序**：旧帧、重放帧、伪造帧一律被识别并拒绝。
5. **失败即终止**：任何认证失败、完整性失败或协议违规，立即清除全部密钥材料并结束会话。

### 2.2 非目标（**本规范不提供**，引用时不得含糊）

| 不提供的性质 | 说明 |
|---|---|
| **后妥协自愈（PCS）** | 棘轮是**纯对称哈希链**，不含 DH 分量。一旦某时刻的会话密钥泄露，攻击者可解密该会话**此后全部**流量，只有重新协商才能恢复 |
| **显式版本面** | 参数集**不含版本字段**（现状）。版本协商与降级阻断是已知的缺口，见 §5.3 与 §12 |
| 第三方可验证的会话证明 | 本规范只做**双方之间**的认证。不导出可供第三方离线验证的令牌 |
| 抗量子 | KEM 为 X25519 |
| 拒绝服务防护 | 攻击者可以丢弃、延迟、伪造连接尝试 |
| 流量形状隐藏 | 帧长度、方向、时序可见。填充策略属于剖面 |
| 多方/群组 | 仅两方 |
| 匿名性 | PSK 认证意味着「知道同一个 PSK 即同一身份」，这是特性不是缺陷 |

> §2.2 是本规范的**硬约束**。下游文档、实现或宣传材料若引用 ZT-DSP，**不得暗示本表所列性质**。

## 3. 威胁模型

### 3.1 攻击者能力

- 完全被动：可记录全部分帧，包括所有明文头字段。
- 完全主动：可注入、删除、重排、复制分帧；可冒充任一方发起新会话。
- **可完全控制传输与中继**：传输层（包括所谓「服务端」）由攻击者实现。
- **不可算**：无法从会话材料反推 PSK（除非 PSK 本身弱）。

### 3.2 攻击面与对应要求

| 攻击 | 核心要求 |
|---|---|
| 窃听 | 全程无明文密钥材料；会话密钥由 PSK 与 DH 共同导出 |
| 中间人 | 确认标签覆盖完整 transcript；对端身份声明进入 transcript |
| 重放 | 单调序号 + 时间窗 + 认证载荷三者合一 |
| 篡改 | AEAD 认证覆盖序号、会话标识与全部载荷 |
| 参数改写 | 参数集进入 transcript，任一项被改写都导致确认失败 |
| 跨会话关联 | 会话密钥逐会话派生；会话标识与身份解绑（是否由剖面保证，见 §9） |

### 3.3 明确承认的风险

- **弱 PSK 是致命的**：低熵 PSK 可被离线穷举。协议层无法修复，只能在部署侧保证熵。
- **PSK 泄露即身份泄露**：持有 PSK 即可冒充。轮换与吊销**不属于**核心规范。
- **DoS 不在防护范围**。

## 4. 协议概览

### 4.1 阶段

```
阶段一  身份声明（可选）    双方声明身份 + 协商参数
阶段二  密钥协商            盐 + 双方临时公钥 → 会话密钥材料
阶段三  确认                双向确认标签，证明双方持有同一 PSK 且 transcript 一致
阶段四  加密帧流（可选）    在通道上传输认证帧
```

- **认证用途只需阶段一至阶段三**。阶段三成功即认证通过。
- **通讯用途使用全部四个阶段**。
- 阶段四对核心是可选的：核心不要求会话必须产生流量。

### 4.2 传输无关性

核心只要求传输提供**有序、可靠的字节流**：不指定 TCP / UDP / QUIC / TLS；不要求全双工；帧边界由协议自身的长度字段给出。

若某剖面需要不可靠传输，**必须由该剖面补齐重传、乱序容忍与会话恢复规则**——核心的「乱序即终止」语义不适用于不可靠传输。

### 4.3 状态机

```
IDLE --阶段一--> ANNOUNCED --阶段二--> AGREED --阶段三--> CONFIRMED --阶段四--> ESTABLISHED
  |                   |                |                |                  |
  +-------------------+----------------+----------------+------------------+
                              任一步失败 → 终止（清除全部密钥）
```

**终止是终态**：不可恢复、不可回退、不可重放进入。

# ZT-DSP 通用协议规范（草案）

ZT-DSP 是一套**基于预共享密钥（PSK）**的双方认证与密钥协商协议。
本文把它写成**与传输无关、与应用无关**的一层，具体用途交给剖面。

## 0. 文档定位

### 0.1 分层

| | 属于核心 | 属于剖面 |
|---|---|---|
| 密码学原语与密钥派生 | ✅ | |
| 阶段编排与状态迁移 | ✅ | |
| 认证成功 / 失败的判定 | ✅ | |
| 防重放、顺序、前向保密 | ✅ | |
| 参数协商 | ✅ | |
| 失败语义（终止并清除密钥） | ✅ | |
| **身份声明的具体形式**（令牌、房间号映射） | | 通讯剖面 |
| **传输选择**（TCP / UDP / QUIC） | | 剖面各自声明 |
| **服务端存在感**（透明中继 / 权威目录） | | 通讯剖面 |
| **元数据防护**（静默丢弃、填充、服务端不可关联） | | 通讯剖面 |
| **应用层载荷语义**（消息、文件、令牌） | | 剖面 / 应用 |

### 0.2 为什么把 PSK 摆在第一位

ZT-DSP 从第一天起就是基于 PSK 的：会话密钥的根材料是 `PSK ‖ X25519 协商值`。
这意味着协议本身已经具备**鉴权**语义：

- **持有 PSK 即持有身份**。知道同一个 PSK 的双方互相认证，不需要证书、目录或 CA。
- **认证与密钥协商是同一件事**。做不到「只认证不建会话」，也没必要分成两步。
- 因此「用 ZT-DSP 做鉴权」不是新增功能，而是**把核心层单独使用**：跑完阶段一至三即拿到认证结论与派生材料，不必进入数据阶段。

本规范因此把「双方相互认证」列为**第一目标**，而不是通讯的附属品。

### 0.3 与 1.0.0 总指导的关系

| | 1.0.0 总指导 | 本文 |
|---|---|---|
| 范围 | 端到端实时通讯协议（含身份令牌、房间号、服务端语义、TCP 承载） | 与传输/应用无关的认证与密钥协商核心 + 剖面 |

差异在于**职责划分**：不再规定「通讯」这一特定用途，也不再规定传输层。

## 1. 术语

| 术语 | 含义 |
|---|---|
| PSK | 预共享密钥。双方事先以带外方式获得的高熵对称秘密，是唯一的信任根 |
| 认证 | 双方证明自己持有同一 PSK，且第三方无法冒充任一方 |
| 密钥协商 | 双方各自产生临时密钥贡献，协商出双方一致、第三方不可计算的共享材料 |
| 会话 | 一次协议运行的结果：认证结论 + 会话密钥 + 会话标识 |
| 通道 | 在会话之上承载有序字节流的抽象，与具体传输无关 |
| 帧 | 通道上的一个完整协议单元，含定长头与载荷 |
| 剖面 | 在核心之上声明的用途约束：追加要求、追加语义、追加威胁模型 |
| 落地时间 | 剖面可以声明的、用于新鲜性判定的本地时钟信息 |

> 核心层**不使用「通讯」作为术语**——通讯只是剖面之一。
